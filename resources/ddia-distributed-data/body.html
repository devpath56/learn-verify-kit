Section 1

Learning goal & roadmap

Learning goal — what you should be able to do when you close this

Given a real design or incident (“can we deploy this schema change?”, “why did that user see their own edit vanish?”, “one shard is at 90% CPU and the rest are idle”, “the node came back and corrupted the file”), you can:

  1. Name the mechanism — which compatibility direction, which replication family, which sharding scheme, which impossibility.
  2. Locate the asymmetry: which side is old and which is new, which node accepts writes, which key is hot, which observer can't tell slow from dead.
  3. Prescribe the fix and name the near-miss you rejected.
  4. State the price. Every one of these costs latency, availability, consistency, operational complexity, or the ability to change your mind later.

The core model in one paragraph

A single machine is a comfortable lie: operations are deterministic, and a fault usually takes the whole thing down rather than leaving you half-working. The moment you have more than one machine, three things stop being true. Code stops being uniform — during any rolling upgrade, old and new versions run simultaneously and must read each other's data. State stops being single — you either keep copies of the same data (replication) or split different data across machines (sharding), and both introduce divergence. And knowledge stops being available — a node cannot tell a slow peer from a dead one, its clock cannot be trusted to order events, and it may itself be paused for a minute without noticing. Parts 1 to 3 build the machinery. Part 4 is the ground truth underneath, and it is the reason every guarantee in the first three parts is hedged.

Tenth-grader version — the whole thing at once

  • Data you save today gets read by programs written years from now — and by programs written years ago that are still running.
  • Once you have more than one computer, you either keep copies of everything everywhere, or you split it up. Both go wrong in their own way.
  • Copies drift apart. Splits go lopsided, and one popular item can ruin the whole scheme.
  • And you can never tell whether the other machine is broken or just slow. Not with a better timeout — ever.

Data outlives code

Compatibility in both directions, and the two ways a schema survives being changed.

Tenth-grader version

  • You save data today. Something reads it in five years — and something written five years ago is still running and reading it too.
  • So data has to be readable by code that is newer than it, and by code that is older than it.
  • The second one is the hard direction: the old program was written before the new format existed, and you can't go back and teach it.
  • Which is why you can add things to a format safely, but removing or renaming things is where people get hurt.

Start with the recipe box

  • A family keeps recipes on index cards in one box. Your grandmother's cards are in the box. So are yours. So will your niece's be.
  • You must be able to read your grandmother's cards — she wrote them before you existed. That direction is easy, because you can look at an old card and work out what it means.
  • Your grandmother must be able to read your cards. That direction is hard, because she wrote her reading habits decades ago. If you invent a new field — “air fryer temperature” — she has to not choke on it, and crucially, she has to copy it out unchanged if she ever rewrites the card, or the information is lost for everyone after her.
  • The box is your database. The cards are records. The people are versions of your code, and they are all in the kitchen at the same time.
“A database generally allows any value to be updated at any time… you may have some values that were written five milliseconds ago and others that were written five years ago… This observation is sometimes summed up as data outlives code.”

The terms, each with its look-alike

TermPlain definitionConcrete exampleBoundary — what it gets confused with
Backward compatibility Newer code can read data written by older code. Your new release reads records written last year. Normally the easy direction: the new code's authors knew the old format existed and could write for it. Confusing the two directions is the single most common error in this area — fix the phrasing by asking whose code is doing the reading.
Forward compatibility Older code can read data written by newer code. An instance that hasn't been upgraded yet reads a record written by one that has. The hard direction, and the one rolling upgrades force on you: the old code was written before the new format existed. It cannot be taught, so the format must be designed so old readers can skip what they don't recognise — and must preserve it if they write the record back.
Rolling upgrade Deploying a new version to a few nodes at a time, monitoring, and working through the fleet. Also called a staged rollout. It's what makes both compatibility directions simultaneously necessary. With client-side applications it's worse: you're at the mercy of the user, who may never install the update.
Field tag
Protocol Buffers		 A number identifying a field in the encoded data, in place of its name. string user_name = 1; — the encoded record carries the tag 1, never the name. You can freely change a field's name, since the encoding never refers to names — but you can never change or reuse its tag, because that would make all existing data invalid. Reserve retired tags in the schema so nobody forgets.
Writer's / reader's schema
Avro		 The schema used to encode, and the schema the reading application expects. Avro resolves the differences by matching fields by name. The writer's schema must be identical to the one used for encoding; the reader's may be an older or newer version. vs Protocol Buffers, where a single schema version does both jobs. Avro's consequence: the data itself identifies nothing — no field names, no types — so it can be decoded only with the writer's schema, which must be conveyed somehow.
Schema evolution Changing a schema over time while keeping old data readable. Adding a field; retiring a field; widening an integer. It gives the flexibility of schemaless storage plus better guarantees and tooling. But keep the number of concurrent schema formats to a minimum, or operations get complicated.
Location transparency The idea behind remote procedure calls: make a network call look like a local function call. EJB, Java RMI, DCOM, CORBA, SOAP. Convenient-seeming and fundamentally flawed. A local call is predictable and fails on parameters you control; a network call fails for reasons entirely outside your control, can time out with no result at all so you don't know whether it happened, may need deduplication because a retry can repeat an action that did succeed, and has wildly variable latency.

How the reader gets the writer's schema at all

Avro's encoding contains no field names or type markers, so it's undecodable without the writer's schema — and including the whole schema per record would erase the space saving. Three answers, by context: a large file of many records puts the schema once at the start (Avro object container files); a database of individually written records stores a version number in each record and keeps a registry of schema versions (Confluent's schema registry for Kafka, LinkedIn's Espresso); two processes on a connection negotiate the schema at setup and use it for the connection's lifetime.

Keeping a registry is worth it regardless: it documents the schemas and lets you check compatibility before anything is deployed.

Concept boundary — what compatibility is not

It is not a property of your database or your language. A schemaless store does not give it to you: the engine stops caring about structure, but your code still expects it.
It is a relationship between a process that encodes and a process that decodes — which means it is always directional, and you must say which process is which before the word means anything.

Same data, many machines

Leaders, followers, lag and its anomalies, conflicts, and quorums.

Tenth-grader version

  • Keep copies of the data on several machines: closer to users, still working if one dies, and more machines to answer reads.
  • Copying data that never changes is trivial. All the difficulty is in copying changes.
  • Copies fall behind, so a reader can see an older version of the world — including one where their own edit hasn't happened yet.
  • And if more than one copy accepts changes, two people can change the same thing at once, and somebody has to decide who wins.

Start with the fridge list

  • A shared shopping list lives on the fridge. One list, everyone writes on it, everyone reads it. No disagreement is possible — but you have to be in the kitchen.
  • So everyone photographs it. Now you can read it from the shop — but your photo is from this morning, and someone has added milk since. You're reading a stale replica.
  • Worse: you add bread to your photo while your flatmate adds bread to theirs. Now there are two lists that disagree, and nothing in the system knows which is right. That is what accepting writes in more than one place costs.
  • The three replication families are three answers to “who is allowed to write on the fridge”: exactly one machine, several machines, or no designated one at all.

The terms, each with its look-alike

TermPlain definitionConcrete exampleBoundary — what it gets confused with
Single-leader replication One replica is the leader and takes all writes; it ships a change stream to the followers, which apply the writes in the same order. Clients may read from any replica. PostgreSQL, MySQL, Oracle Data Guard, MongoDB, Kafka. Consensus algorithms like Raft also elect a single leader. vs multi-leader: writes go to exactly one node, so ordering is decided in one place — which is what makes strong guarantees possible at all. If the database is sharded, each shard has one leader, and different shards may lead on different nodes.
Synchronous / asynchronous Whether the leader waits for a follower's confirmation before reporting success. Semisynchronous in practice: one follower synchronous, the rest asynchronous, promoting another if the synchronous one stalls. Making all followers synchronous is impracticable — any one node outage halts every write. Fully asynchronous means a write confirmed to the client is not guaranteed durable if the leader dies; the upside is the leader keeps working however far behind the followers fall.
Failover Promoting a follower when the leader fails: detect, choose, reconfigure. Detection is almost always a timeout — no response for, say, 30 seconds means assumed dead. vs catch-up recovery, which is the easy follower-failure case: a follower reconnects and requests the changes it missed. Failover is the hard case, and every step of it can go wrong.
Split brain Two nodes both believing they are the leader. If both accept writes with no conflict resolution, data is likely lost or corrupted. Guarding against it by limiting or shutting down old leaders is called fencing (part 4). Careless mechanisms can shut down both nodes — and by the time split brain is detected, corruption may already have happened.
Replication log How the leader tells followers what changed. Three implementations. Statement-based (ship the SQL), WAL shipping (ship the storage engine's write-ahead log), logical / row-based (ship row-level change records — MySQL's binlog). Statement-based breaks on nondeterminism — NOW(), RAND(), autoincrements, triggers. WAL shipping is tightly coupled to the storage engine, so leader and follower usually can't run different versions, which forbids zero-downtime upgrades. The logical log is decoupled, so it can stay backward compatible — and it's parseable by outside systems, which is change data capture. Its own cost: the database must produce a second log on top of the write-ahead log it already keeps for durability — MySQL maintains a separate binlog alongside the WAL; PostgreSQL derives its logical log by decoding the physical WAL.
Eventual consistency Stop writing, wait, and the followers catch up. Normally under a second of lag; near capacity or during network trouble, seconds to minutes. “Eventually” is deliberately vague — there is no limit on how far a replica can fall behind. And it is not a NoSQL property: an asynchronously replicated relational follower behaves exactly the same way.
Quorum
leaderless		 With n replicas, a write must be confirmed by w nodes and a read must query r. If w + r > n, the read and write sets overlap, so at least one node you read has the latest value. n=3, w=2, r=2 tolerates one node down. n=5, w=3, r=3 tolerates two. Common choice: n odd, w = r = (n+1)/2. Quorums need not be majorities — it matters only that the read and write sets overlap. And even with w + r > n the guarantee is soft: concurrent reads and writes, failed writes that partially succeeded, restored-from-old-backup nodes, and rebalancing can all break it. Treat w and r as tuning the probability of staleness, not as absolutes.

A GitHub incident: an out-of-date MySQL follower was promoted to leader. The database used an autoincrementing counter for primary keys, and because the new leader's counter lagged, it reused primary keys the old leader had already assigned. Those keys were also used in a Redis store, so the reuse caused inconsistency between the two — and private data was disclosed to the wrong users.

That is what “discarding the old leader's unreplicated writes” means in practice, and it is why the most important thing in a failover is picking an up-to-date follower: with semisynchronous replication, the one the leader waited for; with asynchronous, the one with the highest log sequence number.

When more than one node accepts writes

  • Multi-leader is worth its complexity in three situations: geo-distributed deployments where every region should take local writes and hide the inter-region delay; offline-capable clients, where each device is a leader and replication lag may be hours or days; and real-time collaboration, where each browser tab holding a shared document is a replica. The libraries doing this are sync engines; an app that keeps working offline is offline-first, and one designed to keep working even if the vendor shuts down its services is local-first.
  • The price is blunt: the consistency multi-leader can achieve is much weaker. You cannot guarantee that a bank account won't go negative, or that a username is unique, because two leaders can each accept a write that is individually fine and jointly illegal. If you need such constraints you are better off with a single leader — this is a fundamental limitation of distributed systems, not a gap in any product.
  • Topologies — circular, star, all-to-all — decide the paths writes take. Circular and star break if one node fails, since they route through it; all-to-all is more fault tolerant but lets messages overtake each other, so a replica can receive an update to a row before the insert that created it. Timestamps cannot fix that, because it is a causality problem rather than an ordering-of-clocks problem; version vectors are what track causality explicitly. Loops are prevented by tagging each write with the identifiers of the nodes it has passed through.
  • Leaderless (Dynamo-style: Riak, Cassandra, ScyllaDB) abandons the leader entirely — clients write to several replicas at once, and there is no such thing as failover. Missed writes are repaired by read repair (a reading client notices a stale replica and writes the newer value back), hinted handoff (another replica holds writes on behalf of an absent one and delivers them later), and anti-entropy (a background process that copies missing data, in no particular order and possibly much later).
  • The structural advantage: a leaderless system does not distinguish the normal case from the failure case. There is no failover decision to get wrong, so one slow or absent replica barely affects response times — the client just uses the faster responses, a technique called request hedging. This is especially valuable against gray failures, where a node is not down but is degraded and unusually slow.

Concept boundary — replication is not backup

It is not a way to recover from mistakes. Replicas reflect writes from one node onto others as fast as they can, so if you accidentally delete data, the deletion is faithfully propagated too.
It is a way to survive machines failing. Backups store old snapshots so you can go back in time — a different purpose, and complementary: backups are often part of setting up a new replica, and archiving replication logs can be part of a backup process.

Different data, many machines

Partition keys, skew and hot spots, the sharding schemes, and what rebalancing costs.

Tenth-grader version

  • When the data no longer fits on one machine, split it up and put each piece somewhere different.
  • Splitting is easy. Splitting so that every machine gets a fair share of the work is the hard part.
  • One extremely popular item can land all the traffic on one machine while the others sit idle — and no clever splitting scheme fixes that by itself.
  • And you have to choose how to split before you know how people will use it. Changing your mind later is expensive.

Start with the encyclopaedia

  • A printed encyclopaedia is split across twelve volumes by the first letters of the entry. To find Tapir you go straight to the right volume — no searching.
  • Notice the volumes aren't evenly lettered: volume 1 covers A–B, volume 12 covers T through Z. The boundaries adapt to the data, because words aren't evenly distributed across the alphabet.
  • Now imagine the entries were filed by date added instead. Every new entry goes into the last volume, so one volume is constantly in use and eleven sit on the shelf. That's a hot shard, and it's caused by the key, not the scheme.
  • The fix — hash the key first — makes every volume equally busy but destroys the thing that made the encyclopaedia useful: you can no longer fetch a range in one place.

Hot keys: the problem hashing cannot solve

Uniformly distributed keys do not mean uniformly distributed load. If one key is genuinely hot, a range-based scheme can at least isolate it — put it in a shard by itself, perhaps on a dedicated machine.

At the application level, the standard trick is to add a random number to the key: two random digits split writes across 100 keys. But be honest about what it buys. Reads must now query all 100 keys and combine the results, so only the write load is split — the read volume is unchanged. It needs bookkeeping to track which keys are split, and a process for promoting a normal key to a split one, since applying the trick to every key would be pure overhead. Load also shifts over time: a viral post is hot for days and then isn't, and some keys are hot for reads while others are hot for writes.

Rebalancing: automatic or manual?

  • Fully automatic rebalancing means less operational work and enables autoscaling — cloud databases advertise adding and removing shards within minutes.
  • But rebalancing is expensive: it reroutes requests and moves large amounts of data. Done carelessly it overloads the network or the nodes. And the system must keep serving writes throughout — near maximum write throughput, the splitting process may not keep up with incoming writes at all.
  • The genuinely dangerous interaction is with automatic failure detection. A node is overloaded and slow; the others conclude it is dead and rebalance load away from it; that adds load to everyone else and the network; more nodes are then falsely suspected. This is a cascading failure caused entirely by the automation.
  • Hence a human in the loop is often worth the slowness — and manual rebalancing lets you pre-emptively prepare for a known event, like a holiday sale or a ticket release.

Secondary indexes and multitenancy — two things sharding makes harder

  • Sharding works well for key-value data. It is harder for relational data, where you may want to search by a secondary index or join records that live on different shards. A write may also need to update related records in several shards, which requires a distributed transaction — available in some databases, but usually much slower than single-node transactions and capable of becoming a system-wide bottleneck.
  • Multitenancy is a common non-scalability reason to shard: give each tenant a shard, or group small tenants together. It buys resource isolation (one tenant's expensive query doesn't hurt others), permission isolation (a bug in access control is less likely to cross tenants when the data is physically separate), per-tenant backup and restore, straightforward GDPR-style export and deletion, data residency, and gradual schema rollout one tenant at a time. Extended to services as well as storage, it becomes a cell-based architecture, where a fault stays inside its cell.
  • The catches: it assumes each tenant fits on one node (if not, you must shard within the tenant too), many small tenants make per-tenant shards wasteful, and any feature that joins data across tenants becomes hard.

Concept boundary — sharding is not the default answer to “we need to scale”

It is not a lightweight tuning step. It adds real complexity: a partition key you must choose before you understand the workload and can barely change later, cross-shard queries that are slow, and cross-shard writes that need distributed transactions.
It is a heavyweight solution mostly relevant at large scale. Replication is useful at every scale; sharding earns its place only when data volume or write throughput genuinely exceeds one machine — and a single machine can do a great deal.

Nothing you're told is reliable

Partial failure, unbounded delay, untrustworthy clocks, zombies — and the fence that saves you.

Tenth-grader version

  • One computer either works or crashes. Many computers can be half-broken, and you can't tell which half.
  • You send a message and get nothing back. Was it lost? Is the machine dead? Did the reply get lost? You cannot tell.
  • Not with a better timeout, not with a faster network — ever. All you can do is guess, and design so a wrong guess doesn't destroy anything.
  • You can't even trust your own clock, or trust that your own program hasn't been frozen for a minute without noticing.

Start with the letter

  • You post a letter asking a question and hear nothing for a fortnight. What happened? Your letter was lost; or it arrived and they're away; or they've died; or they replied and their letter was lost; or it's all just slow.
  • From your side, every one of these looks identical: no reply. You cannot distinguish them, and no amount of waiting turns a guess into knowledge — waiting longer only trades one error for another.
  • So you set a rule: no reply in three weeks, assume they're not coming. That rule is a timeout, and it is a decision, not a discovery.
  • Now the dangerous part. Suppose you assume they're gone and give their job to someone else — and then the original person turns up, having been ill, with no idea they were replaced. Two people now believe they hold the same job. That is the entire safety problem of distributed systems.
“In my limited experience I've dealt with long-lived network partitions in a single data center, PDU failures, switch failures, accidental power cycles of whole racks, whole-DC backbone failures, whole-DC power failures, and a hypoglycemic driver smashing his Ford pickup truck into a DC's HVAC system. And I'm not even an ops guy.”

The terms, each with its look-alike

Partial failure Some parts of the system are broken unpredictably while others work fine. An operation involving several nodes sometimes works and sometimes doesn't — and you may not even know whether it succeeded. vs a single-computer fault, which is deliberately designed to be all-or-nothing: computers prefer to crash outright rather than return a wrong result. Partial failure's defining property is nondeterminism, and that is what makes distributed systems hard.
Unbounded delay An asynchronous packet network gives no guarantee about when — or whether — a message arrives. Round-trip times of several minutes have been observed at high percentiles across cloud regions; even within one datacentre a topology reconfiguration can delay packets by more than a minute. vs a hypothetical synchronous network with a maximum delay d and a maximum handling time r, where 2d + r would be a correct timeout. Fencing token A number the lock service returns with every grant, increasing each time. Every write must carry it, and the storage service rejects any token lower than one it has already accepted. Client 1 holds token 33 and pauses; client 2 acquires token 34 and writes; client 1 wakes and writes with 33, and the storage service rejects it. vs shutting the zombie down (“STONITH”), which is not effective: it can't stop an already-delayed message, and by the time you detect the zombie the damage may be done. Fencing is permanent, unlike optimistic concurrency control, which can be retried. Called sequencers in Chubby, epoch numbers in Kafka.
Byzantine fault A node that lies — sends arbitrary, faulty or contradictory responses. Casting two contradictory votes in one election. vs the assumption made almost everywhere else, that nodes are unreliable but honest: slow, absent, or out of date, but truthful when they do respond. Byzantine tolerance matters in aerospace and among mutually untrusting parties; in a normal datacentre it is impractically expensive and unnecessary.

Why you cannot tell slow from dead

  • Send a request and get no response. The possibilities are: the request was lost; it is queued and will be delivered later; the node failed; the node is paused but will resume; the node processed it and the response was lost; or the response is merely delayed. These are indistinguishable. The only information you have is that you haven't received a reply.
  • TCP doesn't rescue you. It retransmits and reorders, but it can't tell whether the outbound packet or the acknowledgment was lost, and it can't plug a cable back in. Worse: if a connection closes with an error you have no way of knowing how much data the remote node actually processed, and an acknowledgment only proves the remote kernel received it — the application may have crashed before handling it. If you need to be sure, you need a positive response from the application itself.
  • So you use a timeout — and a timeout is a bet with a cost on both sides. Too long, and users wait through an outage. Too short, and you declare live nodes dead: an action may be performed twice, and transferring a slow node's load onto its peers can cascade until everything stops.
  • Network faults are not rare enough to ignore. One study of a medium-sized datacentre found about 12 network faults per month, half disconnecting a single machine and half a whole rack. Redundant networking gear helps less than you'd hope, because it doesn't guard against human error, a major cause of outages.

Clocks are worse than they look, and fail silently

  • Drift. Google assumes up to 200 ppm for its servers — about 6 ms of drift for a clock resynchronised every 30 seconds, or 17 seconds for one resynchronised daily.
  • Sync quality. A minimum error of about 35 ms is achievable over the internet, with occasional spikes to around a second. Some public NTP servers are simply wrong, off by hours.
  • Jumps. A clock too far from its NTP server may be forcibly reset, so applications watching it see time go backward. Leap seconds have crashed many large systems.
  • Silence is the real danger. A defective CPU or misconfigured network breaks loudly. A defective quartz clock or a misconfigured NTP client lets everything seem to work while drifting further from reality — so the result is silent, subtle data loss rather than a dramatic crash. Monitor clock offsets and evict any node that drifts too far.
  • High accuracy is buyable if you must: MiFID II obliges high-frequency trading funds to stay within 100 microseconds of UTC, using GPS receivers, atomic clocks and PTP.

Ordering by timestamp: the trap this sets

  • Client A writes x = 1 on node 1; it replicates to node 3; client B increments to x = 2 on node 3; both replicate to node 2. Clock skew between node 1 and node 3 is under 3 ms — better than you can usually expect.
  • Yet x = 1 carries timestamp 42.004 and x = 2 carries 42.003. B's write is causally later but has the earlier timestamp. Under last write wins, node 2 keeps x = 1 and the increment is silently lost.
  • Three consequences worth memorising: writes can mysteriously disappear, because a node with a lagging clock cannot overwrite a faster node's values until the skew has elapsed; LWW cannot distinguish genuinely concurrent writes from sequential ones, which is what version vectors are for; and two nodes can generate identical timestamps at millisecond resolution, needing a tiebreaker that itself can violate causality.

What you can rely on instead

  • The majority. A node cannot trust its own judgment — it may be semi-disconnected, receiving everything while all its outgoing messages are dropped, protesting “I'm not dead!” to nobody. So decisions, including the decision that a node is dead, are made by quorum. A majority is safe because there cannot be two conflicting majorities at once, and it tolerates a minority failing: one of three, two of five.
  • Fencing tokens. Since zombies cannot be prevented, make their writes harmless. A monotonically increasing token on every grant, carried on every write, and rejected by the storage service if lower than one already seen. A client that has just acquired a lease should write immediately, which fences off any zombie. If your storage supports a conditional write — S3's conditional writes, Azure's conditional headers, Google Cloud Storage's request preconditions — that is enough on its own for a single service.
  • An explicit system model. State your assumptions and design to them. On timing: synchronous (bounded delay, pauses and clock error — unrealistic), partially synchronous (well behaved most of the time, with occasional arbitrary violations), asynchronous (no timing assumptions at all, not even a clock — very restrictive). On nodes: crash-stop, crash-recovery (with stable storage surviving, in-memory state lost), degraded / gray failure (a limping node still passing health checks while doing no real work), and Byzantine. For real systems, partially synchronous with crash-recovery faults is generally the most useful.

Concept boundary — a timeout does not detect anything

It is not a measurement. No timeout can distinguish a dead node from a slow one, because the network has no upper bound on delay and the node has no upper bound on its own pauses.
It is a decision to stop waiting and act on a guess — chosen experimentally by measuring the distribution of round-trip times, and traded off between declaring live nodes dead and waiting too long on dead ones. Design so that being wrong is survivable, which is what fencing tokens and quorums are for.

Answer key

Part 1 · Q1 — the vanishing discount code

(a) Forward compatibility broke. Stated without the word: older code could not correctly read data written by newer code — specifically, instances not yet upgraded encountered a field that did not exist when they were written.

(b) Because reading alone is harmless here; the damage happens on rewrite. An old instance reads the record, doesn't recognise discount_code, drops it from its in-memory representation, and then writes the record back without the field. Orders that were created and never touched again keep the field, because no old instance ever rewrote them. That asymmetry — only modified records lose data — is the fingerprint of this fault.

(c) The encoding must let an old reader skip an unrecognised field and preserve it when writing the record back. In Protocol Buffers the datatype annotation on each field tells the parser how many bytes to skip, which is what makes preservation possible; in Avro the equivalent discipline is that fields are added with defaults and resolved by name. Patching the old code is not the fix because the old code is already deployed and running — that is what makes this the hard direction. Even if you patch it now, the whole point of the property is that it must hold for readers you cannot reach mid-upgrade.

Part 1 · Q2 — the nightly relational dump

(a) Avro, and the structural property is that its schema contains no tag numbers — fields are identified by name. That is precisely why it is friendlier to dynamically generated schemas: you can generate an Avro schema from the relational schema on every run, one record per table and one field per column, and the export process need pay no attention to the schema having changed.

(b) The reader resolves the writer's schema against the reader's schema, matching fields by name. A field present in the writer's schema but absent from the reader's is ignored; a field the reader expects but the writer's schema lacks is filled from the default declared in the reader's schema. Field order does not matter. With Protocol Buffers this same job would require an administrator to maintain the column-to-tag mapping by hand and be very careful never to reuse a tag — exactly the failure they have already hit twice.

(c) The new obligation is conveying the writer's schema, since Avro-encoded data identifies neither field names nor types and is undecodable without it. For this use case — a large file containing many records all encoded with the same schema — the right mechanism is an Avro object container file, which includes the schema once at the beginning of the file. (Credit for naming the other two mechanisms and rejecting them: a per-record version number plus a schema registry suits a database of individually-written records; connection-time negotiation suits two processes on a network connection.)

Part 2 · Q1 — the social app with six followers

(a) Posts vanishing after you create them is a read-after-write (read-your-writes) violation. A comment appearing, disappearing and reappearing is a monotonic reads violation — successive reads are served by replicas with different lag, so the user sees time move backward. The forty seconds lost at failover is discarded unreplicated writes under asynchronous replication.

(b) For read-after-write: read anything the user may have modified from the leader — for a social app the simple rule is own profile and own posts from the leader, everyone else's from a follower. If too much is user-editable, read from the leader for a period after each write, or have the client remember the timestamp of its last write and serve it only replicas that have caught up past it. For monotonic reads: make each user always read from the same replica, chosen deterministically, for example by a hash of the user ID rather than at random. Pinning does not solve read-after-write, because the replica a user is pinned to can still lag behind their own most recent write — consistency of which replica is not the same as freshness of that replica.

(c) At failover a follower is promoted; with asynchronous replication it may not have received the old leader's most recent writes, and the standard resolution is to discard them — so writes confirmed to clients turn out not to have been durable. The decision that limits the damage is choosing the most up-to-date follower: with semisynchronous replication, the follower the leader waited on; with asynchronous, the one with the highest log sequence number. Losing a fraction of a second may be tolerable; promoting a replica days behind would be catastrophic. Credit for naming the GitHub incident's shape — a lagging promoted leader reusing autoincrement primary keys, causing inconsistency with an external store and disclosing private data to the wrong users.

Section 9 continued

Part 2 · Q2 — three regional leaders and two constraints

(a) It is multi-leader replication with asynchronous replication between regions. Neither constraint is enforceable because each leader validates against only its own local state at the time of the write. Two users can register the same username in two regions simultaneously: each write passes the uniqueness check locally, both succeed, and the conflict only surfaces when the writes replicate — after both clients have been told they succeeded. The balance case is the same shape: two withdrawals in different regions can each leave a non-negative balance individually while together taking the account below zero. The constraint spans writes that were never evaluated together.

(b) No — this is not a product limitation. It is a fundamental limitation of distributed systems: if two nodes can accept writes without coordinating, no amount of engineering in the database will let them enforce a constraint that depends on both writes being seen together. Switching vendors will not help. Credit for noting that multi-leader is often a retrofitted feature, so autoincrementing keys, triggers and integrity constraints also interact badly — but that is a separate, weaker point.

(c) Two structural options. Either use a single leader for the data carrying these constraints, accepting cross-region write latency for those operations — possibly while keeping other data multi-leader. Or drop the constraints as hard guarantees and handle violations after the fact: detect duplicate usernames and force a rename, allow the balance to go negative and reconcile. The topology hazard to know regardless: in an all-to-all topology, replication messages can overtake one another, so a replica may receive an update to a row before the insert that created it — a causality problem that timestamps cannot fix and that needs version vectors. I would take the single-leader option for the constrained data: the constraints are stated as product requirements, and the honest cost is latency on those specific writes rather than a class of bug that surfaces as duplicate accounts and negative balances.

Part 3 · Q1 — pings keyed by timestamp

(a) With key-range sharding on a timestamp, shards correspond to contiguous ranges of time. All current writes therefore land in the shard owning the present range, while every other shard holds only historical data and takes no write traffic. The key is at fault, not the scheme: key-range sharding is behaving exactly as designed, and it is the monotonically increasing partition key that concentrates the writes.

(b) Hashing the timestamp would spread the writes evenly, but it would destroy range scans over the partition key, because keys that are adjacent in time would be scattered across every shard. Their main query is “all pings in the last hour” — precisely a range scan over the partition key — so the proposed fix would turn their single most important query into a scatter-gather across all twelve nodes. It trades a hot shard for a slow system.

(c) Make the partition key compound, with something spreading first and the timestamp second — vehicle ID then timestamp. Writes then distribute across shards by vehicle while remaining sorted by time within each vehicle. The cost is that a query spanning all vehicles for a time range now needs a separate range query per vehicle, whose results must be combined. Credit for noting the general principle: keep the partition key's first component spreading and range-scan the later components, so scans stay within a shard.

Part 3 · Q2 — the institutional buyer and the self-healing cluster

(a) Because this is a hot key, not a hot shard. All that buyer's orders share one buyer_id, so they hash to one value and land in one shard no matter how many shards exist. Raising the count from 256 to 4,096 subdivides everything except the thing causing the problem — and it costs an expensive resharding, since every shard must be split and rewritten. Consistent hashing distributes keys uniformly, which is not the same as distributing load uniformly.

(b) Either isolate the hot key — a range-based scheme can put an individual hot key in a shard by itself, potentially on a dedicated machine — or split it at the application level by appending a random suffix, so two digits spread the writes across 100 keys. Be precise about what the second buys: it splits the write load only. Reads must now query all 100 keys and combine the results, so the read volume against that data is unchanged. It also needs bookkeeping to record which keys are split, and a process for promoting a normal key to a split one, since applying it to every key would be pure overhead.

(c) The incident is automatic rebalancing interacting with automatic failure detection. A node was overloaded by the spike and became slow; its peers concluded it was dead and rebalanced its shards away; moving that data added load to the network and the remaining nodes, making them slow, and risking further false suspicions — a cascading failure caused entirely by the automation. I would put a human in the loop for rebalancing, accepting that it is slower in exchange for avoiding operational surprises, and rebalance pre-emptively ahead of known traffic events rather than reactively during them.

Section 9 continued

Part 4 · Q1 — the paused worker and the corrupted file

(a) The first worker became a zombie — a former leaseholder that has not yet discovered it lost the lease and continues acting as though it still holds it, with no awareness that time has passed. The proposed fix cannot eliminate the problem because it only makes the window smaller, never zero: garbage collection pauses can be reduced but not abolished, and the same failure arises with no pause at all if a write request is merely delayed in the network and arrives after the lease has been reassigned — packets can be delayed by a minute or more. Any fix based on making the timing better is fighting an unbounded quantity.

(b) Fencing tokens. The lock service returns a number with every grant that increases each time a lease is issued. Every write to the storage service must carry the client's current token, and the storage service remembers the highest token it has processed and rejects any write carrying a lower one. So worker 1 holds token 33, pauses, and worker 2 acquires 34 and writes; when worker 1 wakes and writes with 33, the service rejects it because it has already accepted 34. On acquiring a lease a client should immediately make a write, because once that write completes any earlier zombie is fenced off. Credit for noting that a conditional-write or compare-and-set facility — S3's conditional writes, Azure's conditional headers, Google Cloud Storage's request preconditions — achieves the same effect for a single storage service.

(c) The popular alternative is shutting the zombie down — disconnecting it from the network, stopping the VM, or powering the machine off, sometimes called STONITH. It is ineffective for two reasons: it does not protect against a delayed write already in flight from a client that has since crashed, and by the time the zombie is detected and shut down the damage may already be done. A third acceptable answer: badly designed shutdown mechanisms can result in all the nodes shutting one another down.

Part 4 · Q2 — writes that never take effect

(a) Under last-write-wins the replica keeps whichever value carries the greatest timestamp and discards the rest. A node whose clock lags is therefore unable to overwrite a value previously written by a node with a faster clock until the skew between them has elapsed. The write is accepted and acknowledged, then silently discarded during conflict resolution — no error is reported to the application, which is why it looks like the write “never took effect”. Sub-5 ms skew does not make this safe because safety here is not a function of how small the skew is: the worked example loses an increment with skew under 3 ms, since what matters is whether the causally-later write happens to receive a smaller timestamp, and any positive skew makes that possible. Correlating with one region is the expected fingerprint of one group of clocks running slightly slow.

(b) The second defect is that last-write-wins cannot distinguish genuinely concurrent writes from sequential ones — writes that occurred in quick succession, where the second causally depends on the first, are treated identically to writes where neither writer knew about the other. The mechanism that addresses it is version vectors, which track causality explicitly rather than inferring it from time. (A third defect worth credit: two nodes can generate the same timestamp at millisecond resolution, needing a tiebreaker that can itself violate causality.)

(c) Because clock faults fail silently. A defective CPU or a misconfigured network breaks loudly and gets fixed quickly; a drifting quartz clock or a misconfigured NTP client lets everything appear to work while diverging further from reality, so the result is silent, subtle data loss rather than a dramatic crash. Nobody is paged, nothing appears in a dashboard, and the loss is discovered — if ever — long afterwards by a user. The operational implication is that you must monitor clock offsets across the cluster and evict any node whose clock drifts too far, because the system will not tell you.
