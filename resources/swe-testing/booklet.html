What this subject asks of you that others don't

Nearly everybody agrees that testing is good, which is exactly what makes this material hard to learn properly: the agreement hides the fact that most of it is a set of trade-offs with stated prices. A test that is easier to write is usually harder to maintain. A double that makes a test fast makes it less truthful. A test that covers more of the system tells you less about where the fault is. So read for the price attached to each recommendation, not for the recommendation. Two habits keep you honest. First, for every practice, ask which specific failure it prevents and what it costs in exchange — if you cannot name both, you have absorbed a slogan. Second, notice how much of this subject is about the test suite as a thing that can itself go wrong: it can be slow, untrustworthy, brittle, unowned, or quietly measuring nothing. The central claim of the whole subject is that a suite in that state is not neutral. It is a liability.

Learning goal & roadmap

Learning goal — what you should be able to do when you close this

Faced with a test suite to design, inherit, or repair, you can:

  1. Classify any test on both axes — the resources it is allowed to consume and the amount of code it validates — and say why the two are distinct and which one the constraints are actually enforcing.
  2. Diagnose a suite that is costing more than it returns, naming whether the problem is brittleness, unclarity, slowness or flakiness, and give the specific remedy and its price.
  3. Choose between a real dependency and each kind of stand-in, and say what each one buys, what it costs in truthfulness, and the condition that makes it the wrong choice.
  4. Say what unit tests structurally cannot tell you, name the gaps a larger test exists to close, and describe the four phases and the two competing properties of the thing being tested.

The core model in one paragraph

Start from what a test is: one behaviour, one specific input, an observable output, and a controlled environment. Thousands of those together tell you how well a product conforms to its intended design and, more importantly, when it does not. But the suite is not a free asset, because tests derive their value from the trust engineers place in them — if testing becomes a productivity sink that constantly induces toil and uncertainty, engineers lose trust and find workarounds, and a bad test suite can be worse than no test suite at all. Everything else follows from protecting that trust. You classify tests on two distinct axes — size, the resources a test may consume, and scope, how much code it validates — and enforce the smallest size available, because speed and determinism are what keep the suite runnable. You aim for a mix weighted heavily toward narrow tests, because they are fast, stable, and pinpoint the fault. Then you write those tests so they never need to be touched again unless the system's requirements change, which means testing through public interfaces and asserting on resulting state rather than on the sequence of calls that produced it. Where the real dependency will not fit inside those constraints you substitute something — but each substitution trades fidelity, and a stand-in that diverges from the thing it replaces produces tests that pass while the system is broken. And finally, none of this can tell you about configuration, load, emergent behaviour, or the unanticipated: a unit test is ensconced in a vacuum, which is exactly what makes it fast and exactly what makes larger tests necessary.

Tenth-grader version — the whole thing at once

  • A test gives the program a known input and checks what comes out. Thousands of them tell you whether the thing still works.
  • Tests are only worth anything if people believe them. Once people stop trusting the tests, the tests are worse than useless — they cost time and change nothing.
  • So keep them fast and keep them reliable. That's why the small ones are restricted to one process and aren't allowed to touch the network.
  • Two different questions: how much is this test allowed to use, and how much of the code is it checking? They're not the same question.
  • Write tests so that changing how the code works doesn't break them — only changing what it does should.
  • Check what the system ended up like, not the exact steps it took to get there.
  • Sometimes the real database won't fit in a test, so you use a stand-in. But a stand-in that behaves differently gives you a green test and a broken system.
  • And small tests live in a vacuum. They can't tell you about bad configuration, heavy traffic, or anything nobody thought of.

What a suite is for

Two purposes, the trust it runs on, the two axes it is classified by, and the arithmetic that decides whether it survives.

Tenth-grader version

  • Tests catch bugs. But the bigger reason to have them is that they let you change things without being frightened.
  • They only work if people believe them. A suite nobody trusts costs time and prevents nothing.
  • Two separate questions about any test: what is it allowed to use (one process? one machine? anything?), and how much code is it actually checking?
  • The small ones can't sleep, can't touch the disk, can't touch the network. That's not fussiness — it's what stops them being slow and unpredictable.
  • Mostly write small, narrow ones. A few medium. Very few enormous. Upside-down versions of that mix have names, and both are bad.
  • A test that fails randomly one time in a thousand sounds fine until you run ten thousand tests a day.
  • Test anything you don't want to break. And don't judge a suite by what percentage of lines it runs — running a line isn't checking it.

The everyday version

A bakery installs an alarm that sounds when an oven runs too hot. For a while it is the most valuable thing in the building: nobody has to stand and watch, and a batch is never lost. Then the alarm starts going off when a door slams, and once or twice for no reason anybody can find. The staff investigate the first few. By the fourth week they glance at it and carry on. By the sixth somebody puts tape over the speaker. Notice what has happened: the alarm still works exactly as well as it did on the first day, and it is now worth less than nothing — it costs money to maintain and it no longer protects anything, and worse, the staff have stopped watching the ovens themselves because they think it is covered. That is the whole economics of a test suite in one object. It is also why the small tests are kept on such a short leash: an alarm that cannot be triggered by a slamming door is not a fussier alarm, it is the only kind that survives contact with a busy kitchen.

The terms, each with its look-alike

TermPlain definitionConcrete exampleBoundary — what it gets confused with
The simplest test Four things: a single behaviour you are testing, usually a method or interface you call; a specific input; an observable output or behaviour; and a controlled environment such as a single isolated process. Taken in aggregate, hundreds or thousands of such tests — a test suite — tell you how well your product conforms to its intended design and, more important, when it doesn't. vs a script that exercises the program. The fourth element is the one people drop, and it is the one the rest of this part is about: without a controlled environment you have an observation, not a test.
The two purposes Catching bugs is only part of the motivation. An equally important reason to test is to support the ability to change. The later in the development cycle a bug is caught, the more expensive it is — exponentially so in many cases. But whether you are adding features, refactoring for code health, or undertaking a larger redesign, tests catch mistakes quickly and make it possible to change software with confidence. If you have a robust testing practice you need not fear change; you can embrace it. vs quality assurance. The consequence is directional: the more and faster you want to change your systems, the more you need a fast way to test them. Writing tests also improves design — as the first client of your code, a test tells you whether the system is too tightly coupled to a database, whether the interface supports the required use cases, and whether the edge cases are handled.
The trust economy Creating and maintaining a healthy suite takes real effort — and tests derive their value from the trust engineers place in them. As a codebase grows so does its suite, and it will begin to face instability and slowness. If testing becomes a productivity sink, constantly inducing toil and uncertainty, engineers will lose trust and begin to find workarounds. This is the load-bearing sentence of the whole subject: a bad test suite can be worse than no test suite at all. It is why speed, determinism and clarity are treated as first-order requirements rather than niceties — each of them is a defence of the trust the suite runs on.
Size The resources required to run a test case — memory, processes, time — and what it is allowed to do. Not its number of lines. Small tests run in a single process (often a single thread), and may not sleep, perform I/O, or make any other blocking call — so no network and no disk, and no third-party program such as a database. Medium tests may span multiple processes, use threads and make blocking calls including network calls to the local machine, but may not reach any other machine. Large tests remove that restriction and may span machines. vs the traditional unit/integration split, and the distinction is deliberate: the most important qualities wanted from a suite are speed and determinism regardless of scope, and small tests are almost always faster and more deterministic. The constraints are not pedantry — they provide a sandbox that prevents engineers from shooting themselves in the foot, and in some cases the infrastructure enforces them.
Scope How much code is being validated by a given test — which is different from how much code gets executed. Narrow-scoped tests, commonly called unit tests, validate the logic in a small focused part of the codebase such as one class or method. Medium-scoped tests verify interactions between a small number of components — a server and its database. Broad-scoped tests validate the interaction of several distinct parts, or emergent behaviours that are not expressed in any single class or method. vs size, with which it correlates but is not identical. When a unit test is called narrowly scoped, that refers to the code being validated, not the code being executed — a class naturally invokes its dependencies while under test. Both mixed cases exist: a broad-scoped test of an endpoint can be small if doubles stand in for everything out of process, and a narrow-scoped test of one method can be medium if validating a single path requires running an entire browser.
The mix, and its two antipatterns A rough guideline: about 80% narrow-scoped unit tests validating the majority of business logic, 15% medium-scoped integration tests validating interactions between components, and 5% end-to-end tests validating the whole system. Unit tests form the base because they are fast and stable, they narrow the scope and reduce the cognitive load of identifying all possible behaviours, and they make failure diagnosis quick and painless. The ice cream cone is many end-to-end tests and few of the others — slow, unreliable, hard to work with, and typical of prototypes rushed to production without addressing testing debt. The hourglass is many end-to-end and many unit tests but few integration tests, which is not quite as bad but still produces end-to-end failures that could have been caught more easily; it appears when tight coupling makes it difficult to instantiate individual dependencies in isolation. vs a rule. Every team's mix will be a little different, and the numbers are by test case count. The reasoning behind the shape is worth keeping: favouring unit tests gives high confidence quickly and early, and larger tests act as sanity checks — they should not be viewed as a primary method for catching bugs. But unit tests cannot verify the interactions between components, such as a contract between two systems built by different teams.
Properties every test should have Hermetic — the test contains all of the information necessary to set up, execute and tear down its environment, and assumes as little as possible about the outside world, including the order in which tests run. They should not rely on a shared database. And a test should contain only the information required to exercise the behaviour in question: keeping tests clear and simple helps reviewers verify the code does what it says, and helps whoever must diagnose the failure. Hence the maxim: a test should be obvious upon inspection. The reason for that maxim is structural — because there are no tests for the tests themselves, they require manual review as an important check on correctness. As a corollary, control flow statements such as conditionals and loops in a test are strongly discouraged: more complex flows risk containing bugs of their own and make the cause of a failure harder to determine.
The arithmetic of flakiness A flaky test fails nondeterministically. At scale, tiny per-test flakiness becomes a daily tax. If each test has even a 0.1% chance of failing when it should not, and you run 10,000 tests per day, you will be investigating 10 flakes per day — each investigation taking time from something more productive. Rerunning failures automatically trades processor cycles for engineering time, which makes sense at low levels, but rerunning a test only delays the need to address the root cause. The real cost is not the investigations: it is that experience suggests the tests begin to lose value as flakiness approaches 1%, because it does not take many flakes before a team stops trusting the suite — and once engineers stop reacting to failures, any value the suite provided is eliminated. Most flakes come from nondeterminism in the tests themselves: clock time, thread scheduling, network latency, and lower-level concerns still.
What to test The straightforward answer: test everything that you don't want to break. If you want confidence that a system exhibits a particular behaviour, the only way to be sure is to write an automated test for it. That includes the usual suspects — performance, behavioural correctness, accessibility and security — and the less obvious ones, such as how a system handles failure. Rather than waiting for a catastrophe to find out how the system responds to one, simulate the common kinds: exceptions and errors in unit tests, injected remote-call errors or latency in larger ones, and disruptions to the real production network. The rule has a sharp organisational edge, usually invoked by teams making changes across an entire codebase: if unrelated infrastructure changes pass all of your tests but still break your product, you are on the hook for fixing it and adding the additional tests. Stated as an aphorism: if you liked it, you should have put a test on it.
Why coverage is a poor answer Code coverage measures which lines of feature code are exercised by which tests. Run 90 of 100 lines and you have 90% coverage. It is often held up as the gold standard for test quality, and that is unfortunate: it is possible to exercise a lot of lines with a few tests, never checking that each line is doing anything useful — coverage measures only that a line was invoked, not what happened as a result. The recommendation is to measure it from small tests only, to avoid the coverage inflation that executing larger tests produces. The more insidious problem is that, like other metrics, it quickly becomes a goal unto itself: a team sets a bar of, say, 80%, and in practice engineers treat the floor as a ceiling — why do more work than the metric requires? The better question set is about behaviours: are you confident everything customers expect to work will work; can you catch breaking changes in your dependencies; are your tests stable? Answering “do we have enough tests?” with a single number ignores a lot of context.
The pitfalls of a large suite Two ways a growing suite turns against you: it becomes brittle, and it becomes slow. Brittle tests over-specify expected outcomes or rely on extensive and complicated boilerplate, so they fail even when unrelated changes are made — a five-line change breaking dozens of unrelated tests. Over time that friction makes a team reticent to perform the refactoring that keeps a codebase healthy. Slow suites are run less often and so provide less benefit; parallel execution and faster hardware are eventually swamped by a large number of individually slow cases. Two named causes worth carrying. Some of the worst brittleness comes from the misuse of mock objects — treated in Part 3. And a specific slowness trap: calls to sleep and timeout functions used as naive heuristics before checking a nondeterministic result. Half a second here or there looks harmless, but embedded in a widely used utility it adds minutes of idle time to every run. The better solution is to actively poll for the state transition at a frequency closer to microseconds, combined with a timeout in case the state is never reached.
Living with a large suite The secret is to treat it with respect — and specifically, to treat your tests like production code. Incentivise engineers to care about their tests, and reward them as much for having rock-solid tests as for a great feature launch. Set performance goals and refactor slow or marginal tests. When simple changes begin taking nontrivial time, spend effort making the tests less brittle. And invest in infrastructure — linters, documentation and other assistance that makes it more difficult to write bad tests. vs discipline. The stated failure mode is economic, not moral: engineers who encounter unbearable tests find ways around the slowdown, some going as far as skipping tests entirely when submitting changes. That is risky and should be discouraged — but if a suite is causing more harm than good, eventually engineers will get their job done, tests or no tests. Reducing the number of frameworks and tools you must support increases the return on every hour spent improving them.
The limits of automation Automated testing is not suitable for all testing tasks. Judging the quality of search results involves human judgement; so does capturing the nuances of audio and video quality. And humans are better than automated systems at searching for complex security vulnerabilities. The general form is exploratory testing: a fundamentally creative endeavour in which someone treats the application as a puzzle to be broken, perhaps by executing an unexpected set of steps or inserting unexpected data — the specific problems to be found are unknown at the start and are gradually uncovered by probing overlooked code paths and unusual responses. vs an argument for manual testing. The relationship is a pipeline: as soon as an exploratory test discovers an issue, an automated test should be added to prevent future regressions, and a flaw found by a human can then be run continuously and at scale. Automating the well-understood behaviours is what frees the expensive and qualitative human effort for the parts where it adds most — and avoids boring the testers to tears.

Concept boundary — the suite is an asset only while it is believed

What it sounds like: tests are a safety net, so more of them is better, and a slow or noisy suite is at worst a mild inconvenience — still better than nothing.
What it actually is: a claim that the suite's entire value is mediated by human behaviour. Its value is realised only when somebody reads a failure and acts on it. That makes trust the currency, and trust is destroyed by exactly the things this part constrains: nondeterminism, slowness, brittleness and obscurity. Hence the sentence that anchors the subject — a bad suite can be worse than no suite at all — which is not rhetoric but arithmetic, since a suite people have stopped believing costs maintenance, costs investigation time, and has additionally stopped anyone from watching the system themselves.
Why that matters practically: it tells you what the size constraints are really for. Forbidding a small test from sleeping, touching disk or reaching the network is not about purity. Each prohibition removes a source of slowness or nondeterminism, which are the two things that erode belief fastest — and the reason larger sizes are permitted at all is that some risks cannot be covered any other way, at a price you should pay knowingly.
The trap: measuring the suite with a number that ignores belief. Coverage is the classic case: it records that a line ran, not that anything checked it, and the moment it becomes a target the floor turns into a ceiling. The questions that actually assess a suite are about behaviours and confidence — will the things customers rely on keep working, will you catch a breaking change in a dependency, and do people still act on a red result.

Tests that never need changing

The two ways a test turns into a liability, and the practices that stop a suite becoming the thing that resists change.

Tenth-grader version

  • The ideal test is one you write once and never touch again — unless what the system is supposed to do changes.
  • Two things go wrong. A test breaks when nothing was actually broken. Or a test fails and nobody can work out what it was ever for.
  • Test through the front door — the same way real users call the code. If you test the private bits, every tidy-up breaks a test.
  • Check what the system ended up like, not the exact list of calls it made along the way. There's more than one way to get the right answer.
  • Write one test per behaviour, not one per method. Methods do several things; behaviours don't.
  • Name the test after the behaviour. If you need the word "and" in the name, it's two tests.
  • No loops or if-statements in tests. Nothing checks the test, so it has to be obviously right just by looking.
  • A bit of repetition is fine in tests. Clever sharing that hides the details is not.

The everyday version

A landlord wants to know that a flat's front door still locks. There are two ways to check. The first: turn the key from the outside and try the handle. The second: take the lock apart, note that the third pin sits at 4.1 millimetres and the cam rotates 38 degrees, and assert those numbers. Both confirm the door is locked today. But replace the lock with a better one, or have the locksmith adjust the mechanism, and the second check screams while the door is as secure as ever — and the landlord, who has been woken at 3 a.m. by that alarm four times, eventually disconnects it. Notice the second failure too: two years on, nobody can remember why 38 degrees was the number, or whether it still should be. The first check has neither problem. It survives any change to the mechanism and fails only when the door genuinely does not lock, and anybody reading it can see in one line what it was for.

Brittleness A brittle test fails in the face of an unrelated change to production code that does not introduce any real bug. In a small codebase with a few engineers, tweaking a few tests per change may not matter. The four kinds of change The framework that makes “unchanging” precise. The ideal test never needs to change unless the requirements of the system under test change. Pure refactoring — internals change, the interface does not; tests should not need to change, since their role is to confirm the refactoring did not change behaviour. New features — existing behaviours are unaffected, so you write new tests and touch no old ones. Bug fixes — the bug means a case was missing, so the fix brings the missing test with it, again touching nothing existing. Behaviour changes — the one case where existing tests are expected to change. Each of the first three has a diagnostic edge: a test that must change during a refactoring means either the change is not a pure refactoring, or the tests were not written at an appropriate level of abstraction. The fourth is qualitatively different and much more expensive, because users rely on current behaviour: changing a test here means you are breaking an explicit contract, whereas changes in the other three mean you were relying on an unintended contract.
Test via public interfaces By far the most important practice: invoke the system being tested in the same way its users would, calling its public surface rather than its implementation details. The argument is airtight by construction: if tests work the same way as the system's users, a change that breaks a test might also break a user. Peering into internal state or calling methods that are not publicly exposed means almost any refactoring — renaming a method, extracting a helper class, changing a serialisation format — breaks the test, even though the change is invisible to real users. “Public” here means the surface exposed to third parties outside the team that owns the code, which does not always match a language's visibility keywords. Defining the scope of a unit is more art than science; three rules of thumb. A class existing only to support one or two others probably should not be considered its own unit and should be tested through them; anything designed to be used without consulting its owners almost certainly constitutes a unit and should be tested directly; and a general-purpose support library accessible only to its owners is also a unit — the resulting redundancy is valuable, since without it removing one caller could silently open a coverage gap.
State, not interactions Two ways to verify. With state testing you observe the system itself after invoking it. With interaction testing you check that it took an expected sequence of actions on its collaborators. Interaction tests are more brittle for the same reason testing a private method is: they check how a system arrived at its result, whereas usually you should care only what the result is. Verifying that a particular call was made against a database fails in both directions — if a bug deletes the record immediately afterwards the test still passes, and if the system is refactored to call a slightly different interface to write an equivalent record the test fails though nothing is wrong. vs a stylistic preference. The named cause is over-reliance on mocking frameworks, which make it trivial to create doubles that record and verify every call — a strategy that leads directly to brittle interaction tests. Hence the stated preference for real objects over mocked objects, as long as the real objects are fast and deterministic. Part 3 takes the subject up properly.
Complete and concise A test is complete when its body contains all the information a reader needs to understand how it arrives at its result, and concise when it contains no other distracting or irrelevant information. The failing case has both defects at once: a constructor loaded with irrelevant arguments, and the values that actually matter buried in a helper, leaving the reader asking where the expected number came from. The fix pulls the meaningful inputs into the test body and pushes the irrelevant construction into a helper. vs short. The two pull in opposite directions and both must hold — which is why the resolution is often to violate deduplication if it leads to clearer tests. The test to apply: a test's body should contain all the information needed to understand it, without containing any irrelevant or distracting information.
Behaviours, not methods A behaviour is any guarantee a system makes about how it will respond to a series of inputs while in a particular state — expressible as given, when, then. The instinct is to mirror the code's structure, one test method per production method. It is convenient at first and degrades: as the method grows more complex, so does its test. Framing tests around methods encourages unclear tests because a single method often does a few different things under the hood and might have several tricky edge cases. The mapping is many-to-many: most nontrivial methods implement multiple behaviours, and some behaviours rely on the interaction of multiple methods. Behaviour-driven tests are clearer for three stated reasons: they read more like natural language rather than requiring laborious mental parsing; they express cause and effect more clearly because each is limited in scope; and being short and descriptive, they make it easier to see what is already tested and encourage adding new streamlined tests instead of piling onto existing ones. Structure them so the three parts are explicit, which lets a reader work at three levels — the name, then the given/when/then, then the code. The common violation is interleaving assertions among multiple calls, merging “when” and “then” so the action cannot be distinguished from the expected result.
Naming after the behaviour A test's name should summarise the behaviour it tests: both the actions being taken on the system and the expected outcome, sometimes with the prior state. The name matters because it is often the first or only token visible in failure reports — your best opportunity to communicate the problem when the test breaks — and the most direct expression of the test's intent. Names are far more verbose than production code would tolerate, and that is fine: you never write code that calls them, and humans read them in reports. A useful trick when stuck is to start with “should”, so that class and test name read as a sentence. vs naming after the method under test, which is the method-oriented habit. The naming rule doubles as a scope check: if you need the word “and” in a test name, there is a good chance you are testing multiple behaviours and should be writing multiple tests. Reading all the test names in a suite should give a good sense of the behaviours the system implements.
No logic in tests Clear tests are trivially correct upon inspection. Logic — operators, loops, conditionals — forces mental computation instead of reading the answer off the screen. Production code must generalise over any input, so it earns its logic and has tests to check it. Test code does not have that luxury: if you feel you need to write a test to verify your test, something has gone wrong. The worked case is a single string concatenation building an expected URL, which quietly conceals a doubled separator; writing the expected value out in full makes the bug immediately visible. vs duplication being bad. The lesson is that duplicating the value was a small price to pay for making the test more descriptive and meaningful. And the risk scales: if humans are bad at spotting bugs from string concatenation, they are worse at spotting them in loops and conditionals — so stick to straight-line code over clever logic, and tolerate some duplication when it makes the test more meaningful.
Clear failure messages The last aspect of clarity concerns not how a test is written but what an engineer sees when it fails. Ideally they could diagnose the problem from the message alone, without opening the test. A good message contains much the same information as the test's name: the desired outcome, the actual outcome, and any relevant parameters. “Test failed: account is closed” leaves the reader unable to tell whether the closure was the cause or the unmet expectation; naming both the expected state and the actual object removes the ambiguity. vs an assertion library's default output, which is only as informative as what you handed it. An assertion given nothing but a boolean can say only that it expected true and got false; one given the subject can report which collection failed to contain what. Where no such helper exists, it should always be possible to specify the important information manually.
Descriptive over deduplicated Production code aims to avoid repetition so that a concept lives in one place. Test code should instead favour descriptive and meaningful phrases — a little duplication is fine so long as it makes the test simpler and clearer. The cost/benefit differs for two reasons. Deduplication earns its keep by making change easier, but good tests are designed to be stable and you usually want them to break when the system changes — so the benefit is smaller. Meanwhile the cost of complexity is larger, because production code has a test suite to keep it honest as it grows complex, whereas tests must stand by themselves. The failing example hides its inputs and its assertions behind helpers full of logic, so the reader cannot see the case being tested — or the bug in the helper. The two principles are complementary, not opposed: helper methods and infrastructure still make tests clearer by removing repetitive steps whose details are irrelevant to the behaviour under test. The test is the motive — refactor toward descriptive and meaningful, not solely to reduce repetition. Three specific patterns follow in the next row.
Three ways tests share code Shared values, shared setup, and shared helpers — each useful and each with a characteristic failure. Values: a bank of shared constants makes tests concise and makes it hard to see why a particular value was chosen; better-named constants help a little but still obscure the detail and tempt reuse where the name does not quite fit. The better technique is a helper that sets sensible defaults and lets each test specify only the values it cares about. Setup: best used to construct the object under test and its collaborators when most tests do not care about the arguments — but a test that does care about a particular value should state that value directly, overriding the default, rather than leaving a reader hunting for where it came from. Helpers: a general validate method called at the end of every test is the bad extreme — such tests are less behaviour-driven, their intent is hard to determine, and a single bug makes a large number of them fail at once. The good version of a validation helper is narrow: the best ones assert a single conceptual fact about their inputs, and they earn their place when that fact is conceptually simple but needs looping or conditional logic that would reduce clarity inside the test body. Beyond a single suite, shared code becomes test infrastructure, which is closer to production code than to test code: it has many callers, is hard to change without breakages, must be treated as its own product, and must always have its own tests.

Concept boundary — a test is a contract, and you choose which one

What it sounds like: a list of style preferences about how to write tests — front door rather than back, state rather than calls, behaviours rather than methods, a bit of repetition rather than clever helpers. Agreeable, and easy to treat as taste.
What it actually is: one idea applied four times. Every test asserts a contract, and you get to choose whether that contract is the one your users actually depend on or an accidental one nobody promised. Test the private method and you have contracted the internal structure. Assert the call sequence and you have contracted the route rather than the destination. Write one test per method and you have contracted the code's shape. Each choice makes a change that breaks nothing real break a test — which is the definition of brittleness.
Why that matters practically: it gives you a diagnostic instead of a rulebook. When a test breaks during a refactoring, the question is not “which rule did we violate?” but “what did this test contract that we never promised?” And it explains why behaviour changes are the one legitimate reason to edit an existing test: there you really are breaking an explicit contract, and the cost of updating tests is small next to the cost of updating every user.
The trap: treating clarity as the softer half of the list. Clarity is what makes the contract inspectable, and it has a hard structural justification — there are no tests for the tests, so manual reading is the only check on their correctness. That is why logic is forbidden rather than discouraged, why a little duplication is a bargain, and why a test nobody can decipher is worse than absent: it will eventually be deleted, having provided nothing for however many years it existed.

Standing in for the real thing

The three ways to substitute a dependency, what each one costs in truthfulness, and why the real implementation usually wins.

Tenth-grader version

  • Some things can't be in a test — a real payment service, a real database. So you put in a stand-in.
  • Three kinds. A fake is a simple working version. A stub just returns whatever answer you told it to. An interaction check doesn't answer at all — it only records that it was called.
  • First choice is still the real thing. Tests that run the actual code tell you more.
  • If the real thing is too slow, too unpredictable, or too painful to build, then substitute.
  • A fake is best, because the code being tested can't tell the difference. But somebody has to write it and keep it honest — so it needs its own tests.
  • Stubbing is quick and it hardcodes an assumption. If the assumption is wrong, your test passes and the system is broken.
  • Checking which calls were made is the weakest option: it can only tell you the code tried, never that it worked.

The everyday version

A flight school cannot practise engine failure by switching off a real engine over a city. So it substitutes. A simulator is a working model: it flies wrong when you fly it wrong, so the trainee cannot tell the difference from inside — which is exactly what makes it useful, and exactly why somebody has to keep it matched to the real aircraft as the aircraft changes. A scripted answer is cheaper: the instructor simply says “assume the left engine is out”. Fast, flexible, able to produce situations no simulator would generate — and it teaches whatever the instructor happened to assume, so if the real aircraft yaws the other way, the trainee has practised the wrong thing. And the weakest substitute is a checklist observer who does not fly anything and only records that the trainee reached for the correct lever. That confirms the drill was attempted. It cannot confirm the aircraft would have stayed in the air. All three have their place, and the ranking never changes: fly the real aircraft where you safely can, simulate where you cannot, script sparingly, and treat “they reached for the lever” as the last resort it is.

The word mocking is often used for all of this, and is avoided here because it also names something narrower. Substitution introduces three complications. Testability — the codebase must be designed so tests can swap implementations, and retrofitting that later can require a major refactor. Applicability — improper use produces tests that are brittle, complex and less effective, and the damage is magnified across a large codebase. Fidelity — how closely the double's behaviour resembles the real thing.
Seams and dependency injection Code is testable if it is written so unit tests can be written for it. A seam is what makes that possible: a way to use different dependencies for the system under test than the ones used in production. Dependency injection is the common technique: rather than a class instantiating what it needs, those dependencies are passed to it, so they can be substituted in tests. Production passes the implementation that talks to an external server; the test passes a double. Frameworks exist to construct object graphs automatically and remove the boilerplate. vs a universal requirement. In dynamically typed languages it is possible to replace individual functions or methods directly, which makes injection less important there, because you can keep the real dependency and override only the parts unsuitable for tests. The timing point is the one to keep: writing testable code requires an upfront investment, and it is especially critical early, because the later testability is considered the harder it is to apply — code written without testing in mind typically needs refactoring or rewriting first.
Technique 1 — faking A fake is a lightweight implementation of an interface that behaves similarly to the real implementation but is not suitable for production — an in-memory database, an in-memory file system. It is often the ideal technique when you need a double, because it behaves like the real thing: the system under test should not be able to tell whether it is interacting with a real implementation or a fake. It stores state, so a value written can be read back. vs a convenience. A fake is real work: one might not exist for the object you need, and writing one is challenging because you must ensure it has similar behaviour to the real implementation now and in the future. That maintenance burden is why ownership matters, treated three rows below.
Technique 2 — stubbing Giving behaviour to a function that otherwise has no behaviour of its own — you specify exactly what values it returns. Typically done through a mocking framework, to avoid the boilerplate of hand-writing classes that hardcode return values. It is quick and simple to apply. vs faking. A fake implements the contract; a stub asserts a fragment of it. That difference generates all three of stubbing's dangers, two rows below.
Technique 3 — interaction testing Validating how a function is called without actually calling the implementation of the function. The test fails if it is not called, is called too many times, or is called with the wrong arguments. Also typically done through a mocking framework, which removes the boilerplate of hand-writing classes that count calls and record arguments. This is the thing that is sometimes called mocking — a terminology avoided here because mocking frameworks do stubbing as well. It is useful in certain situations but should be avoided when possible, because overuse easily results in brittle tests. Conditions are set out in the last two rows.
The real implementation first The first choice is the same implementations used in production code. Tests have higher fidelity when they execute code as it will be executed in production. Preferring real implementations is called classical testing; preferring frameworks is called mockist. Realism beats isolation because a test full of doubles isolates the system from its dependencies, and then an engineer may need integration tests or manual checks to reach the same confidence — extra work that slows development and lets bugs through when people skip it. Two arguments beyond fidelity. Replacing all dependencies arbitrarily isolates the system to whatever the author happened to put in that class and excludes implementation that happens to live in another class — but a good test should be written in terms of the API being tested rather than how the implementation is structured. And when a real dependency has a bug and your test fails, this is good: it means your code will not work properly in production, and good continuous-integration tooling makes it easy to find the change responsible.
When a real implementation is not the answer A real implementation is preferred if it is fast, deterministic and has simple dependencies — a value object, a date, an amount of money, a collection. Three considerations decide the rest. Execution time: there is no exact threshold. One extra millisecond per case is nothing; one extra second may be reasonable across five cases and not across five hundred. For borderline cases it is often simpler to use the real implementation until it becomes too slow, then switch. Determinism: a real implementation is more complex and so likelier to be nondeterministic — multithreading whose output depends on scheduling, code that is not hermetic and depends on an external service, code that reads the system clock. Dependency construction: a real object needs its entire dependency tree built, and those tests need maintenance whenever a constructor signature changes. vs a rule you can apply mechanically — the material is explicit that trade-offs must be made. Two counterweights. Rare flakiness might not warrant a response, because there is little disruption; frequent flakiness means it is time to substitute. And on construction, the ideal answer is not a double but the same object-construction code used in production — a factory method or automated injection — which requires that code to be flexible enough to accept doubles.
The fidelity of a fake How closely the behaviour of a fake matches the real implementation. If they diverge, a test using the fake is not useful — it might pass while the same code path fails against the real implementation. Perfect fidelity is not always feasible; the fake exists precisely because the real thing was unsuitable, so a fake database will not match a real one on disk storage. Primarily, a fake should maintain fidelity to the API contracts of the real implementation: for any given input it should return the same output and make the same state changes — if saving an item succeeds for a new identifier and errors for an existing one, the fake must do the same. One way to think about it: the fake must have perfect fidelity to the real implementation, but only from the perspective of the test. A fake hashing function need not produce the same hash values, only unique ones per input, provided the contract makes no promise about specific values. Latency and resource consumption are usually outside the needed fidelity too — but you cannot use a fake if you need to test those constraints explicitly. And a fake need not implement everything: for unsupported paths it is best to fail fast, which tells the engineer the fake is not appropriate here.
Who owns a fake, and why it needs tests Because a fake must track the real implementation's behaviour as that behaviour changes, the team that owns the real implementation should write and maintain the fake. The economics are explicit: a fake requires more effort and more domain expertise to create, and a team should weigh whether the productivity gain outweighs the cost — for a handful of users it may not be worth it; for hundreds it is an obvious win. To limit how many exist, create a fake only at the root of the code that is not feasible to use in tests: if a database cannot be used, fake the database interface itself rather than every class that calls it. The correctness requirement is absolute: a fake must have its own tests to ensure it conforms to the API of its real counterpart, or its behaviour will diverge over time as the real implementation evolves. The technique named for this is a set of tests written against the public interface and run against both the real implementation and the fake — the real-implementation runs are slower, but only the fake's owners need to run them. If no fake exists: ask the owners, since they may not know the concept or its benefit; failing that write your own by wrapping the calls in a single class and faking that; failing that, fall back to the real implementation or another technique.
The three dangers of overusing stubbing Because stubbing is so easy to apply, it is tempting whenever a real implementation is not trivial. Overuse costs three specific things. Tests become unclear: the extra code defining stubbed behaviour detracts from the intent of the test and is hard to follow if you do not know the implementation. Tests become brittle: stubbing leaks implementation details of your code into your test, so a change to how the code works forces a test update, when a good test should change only if user-facing behaviour changes. Tests become less effective: there is no way to ensure the stubbed function behaves like the real one, so you duplicate part of the contract with no guarantee it is correct — and there is no way to store state, so you cannot save an item and then read it back. The diagnostic worth memorising: a key sign that stubbing is not appropriate is finding yourself mentally stepping through the system under test in order to understand why certain functions are stubbed. The worked contrast is stark — a test with five stubbed calls can only end by verifying that one of them happened, whereas removing the stubbing lets the same test query the resulting state, and it becomes shorter, needs no special setup, and stops exposing how the internals fit together.
When stubbing is appropriate Not as a catch-all replacement, but when you need a function to return a specific value to get the system under test into a certain state. Because the behaviour is defined inline, stubbing can simulate a wide variety of return values or errors that might not be possible to trigger from a real implementation or a fake — which is its unique capability. Two constraints keep it honest. Each stubbed function should have a direct relationship with the test's assertions, so its purpose is clear. And a test should stub a small number of functions, because a test requiring many stubs is a sign that stubbing is being overused, or that the system under test is too complex and should be refactored. Even where appropriate, real implementations and fakes remain preferred: they do not expose implementation details and they give more guarantees about correctness.
When interaction testing is warranted State testing is preferred; interaction testing is the fallback. Its primary issue: it cannot tell you that the system under test is working properly — only that certain functions were called as expected. That forces an assumption — if the save call is made, we assume the item was saved — whereas state testing actually validates the assumption, by saving and then querying. It also uses implementation details, since proving a function was called exposes to the test that the system calls it. Tests that overuse it are jokingly called change-detector tests, because they fail in response to any change to production code even when the behaviour is unchanged. Two cases warrant it: when you cannot perform state testing because no real implementation or fake is usable; and when differences in the number or order of calls would cause undesired behaviour — verifying that a cache reduces database reads, for example. Two practices reduce the damage. Perform interaction testing only for state-changing functions — those with side effects on the world outside the system under test, such as sending an email or saving a record — because for non-state-changing functions the check is usually redundant: the system will use the return value to do work you can assert on, and the interaction itself is not important for correctness. And avoid overspecification: verify the minimum necessary for the behaviour under test, so unrelated changes do not fail the test and a reader can tell which assertions matter. Finally, it is not a complete replacement — where a unit test can only check interactions, consider supplementing with a larger-scoped test that checks state.

Concept boundary — every substitution is a purchase, and fidelity is the currency

What it sounds like: a menu of interchangeable tools for the same job. You need the database out of the test, so pick whichever technique is most convenient — the framework makes all three about equally easy to write.
What it actually is: a ranked ladder, and each rung down buys speed and control by spending truthfulness. The real implementation runs the code that will run in production. A fake runs different code that honours the same contract, so the system under test cannot tell — which is why it is the best substitute and also why somebody must keep it matched. A stub honours no contract at all; it replays one answer the test author believed was right, so it encodes an assumption that nothing checks. And an interaction check does not even claim an answer: it records that a call happened, which is compatible with the operation having done nothing, or having been undone a line later.
Why that matters practically: it tells you what a green test is worth. With a real implementation or a fake, green means the behaviour happened. With a stub, green means the behaviour happened if the author's belief about the dependency was accurate. With an interaction check, green means the attempt was made. Those are three different claims, and the last one is compatible with a broken system — which is why the fallback carries an instruction to supplement it with a larger-scoped test that checks state.
The trap: letting ease of writing choose. The framework makes the weakest options the fastest to type, and the cost arrives later and elsewhere — in tests that need constant maintenance while rarely finding bugs, and in an interface owner discovering that thousands of tests have hardcoded beliefs about their contract, some of which were never true.

What small tests cannot tell you

The gaps a vacuum leaves, the quantity that closes them, and what a larger test costs to build, run and own.

Tenth-grader version

  • Small tests are fast and reliable because they cut the system off from the real world. That's also what they can't see.
  • Five blind spots: stand-ins that don't match reality, broken configuration, behaviour under heavy traffic, things nobody thought of, and behaviour that only appears when the parts run together.
  • Bigger tests fix those and break every rule that made the small ones nice: they're slow, they're flaky, and they're hard to run lots of.
  • Two more problems that are about people, not machines: nobody's sure who owns them, and everyone builds them differently.
  • Every big test has the same four steps: get a copy of the system, put data in it, do something, check what happened.
  • The copy can be more realistic or more isolated. You usually can't have both.
  • Keep them as small as you can while still being realistic — and make sure a failure tells you something you can act on.

The everyday version

A car maker tests a new brake design on a rig: the caliper is clamped in a jig, a motor spins a disc, and a sensor measures the stopping torque a thousand times an hour, every result identical. It is fast, repeatable, and it will catch a bad batch of pads immediately. But notice what the jig has removed in order to be repeatable — the weight of the car, the temperature of a mountain descent, the wiring loom, the software that decides how hard to squeeze, the wheel it was bolted to by a person, and the rain. Every one of those is a real cause of brake failure and not one of them can appear on the rig, because removing them is exactly what made the rig fast. So you also drive the car. That costs a track, a day, a driver, and it produces results that vary between runs, which is precisely the price of putting the world back in. The rig is not wrong; it simply answers a smaller question than the one you eventually have to answer. And the crucial detail: if the jig's sensor and the real wheel disagree by ten percent, every one of those thousand identical results is ten percent wrong, all at once.

The terms, each with its look-alike

TermPlain definitionConcrete exampleBoundary — what it gets confused with
Larger tests Tests not bound by the small-test constraints. They may be slow, may be nonhermetic, and may be nondeterministic. Default timeouts of fifteen minutes or an hour are normal, and some run for hours or days. They may share resources with other tests and with traffic — and once a test is nonhermetic, it is almost impossible to guarantee determinism, because other tests or user state may interfere. vs a failure of discipline. The justification is a question about your own habits: you run unit tests as you go, and then you run the actual binary and try it out — and when you hand the code to somebody else, they try it out too. Unit tests give confidence about individual functions, objects and modules; large tests give more confidence that the overall system works as intended — and automating that scales in a way manual trying-out does not.
Fidelity The property by which a test is reflective of the real behaviour of the system under test. It is the primary reason larger tests exist. One way to see it is the environment: a unit test bundles a test and a small portion of code into a runnable unit, which ensures the code is tested but is very different from how production code runs; production itself is the environment of highest fidelity, with a spectrum of interim options between. The other way is the test content: hand-crafted data covers a narrow range of cases and tends to conform to the biases of the author, while data copied from production is more faithful precisely because it was captured that way. vs realism as an unqualified good. Increasing fidelity also comes with increasing costs and — in the case of production — increasing risk of failure, so the job is to find the proper fit rather than to maximise it. The scenarios that hand-crafted data misses are named directly: they are a fidelity gap in the tests.
Gap 1 — unfaithful doubles When a heavyweight dependency is replaced, it becomes possible that the replacement and the doubled thing do not agree. The mechanism is social. Almost all unit tests are written by the same engineer writing the unit under test, so when doubles are needed it is that engineer who defines the double and its intended behaviour — and they usually did not write the thing being doubled and can be misinformed about its actual behaviour. The relationship between a unit and its peer is a behavioural contract; if the engineer is mistaken about the actual behaviour, the understanding of the contract is invalid. And doubles become stale: if the double is not visible to the author of the real implementation and that implementation changes, there is no signal that the test and the code should be updated. Note the escape hatch, which is Part 3's conclusion restated: if teams provide fakes for their own services, this concern is mostly alleviated.
Gap 2 — configuration Unit tests cover code within a binary, but that binary is typically not completely self-sufficient in terms of how it is executed. There is usually a deployment configuration or a starter script, and real production instances have their own configuration files or databases. Problems in those files, or incompatibility between the state they define and the binary, can lead to major user issues that unit tests alone cannot verify. The scale of this gap is the striking part: configuration changes are the number one reason for major outages. Configurations tend to be written in configuration languages rather than production languages, they often have faster rollout cycles than binaries, and they can be harder to test — all of which raises the likelihood of failure. Hence the practice attached: keep configuration in version control alongside code, so that a change to it can be identified as the source of a bug rather than appearing as random external flakiness — and so it can be built into larger tests.
Gap 3 — behaviour under load Performance, load and stress testing often require sending large volumes of traffic to a binary, which does not fit the model of a typical unit test. Unit tests are meant to be small and fast so they fit standard execution infrastructure and can run many times in a frictionless workflow. The volumes needed to provoke load problems can be thousands or millions of queries per second. Load and stress handling are described as highly emergent properties: complex behaviours that belong to the overall system but not to its individual members — which is why they cannot be decomposed into smaller tests, and why such tests must be made to look as close to production as possible.
Gaps 4 and 5 — the unanticipated, and the vacuum Unit tests are limited by the imagination of the engineer writing them — they can only test for anticipated behaviours and inputs. But the issues users find are mostly unanticipated; if they had been anticipated they would be unlikely to reach users at all. Hyrum's Law sharpens this: even if you could test completely for conformance to a strict specified contract, the effective user contract applies to all visible behaviours, not just a stated one, and unit tests alone are unlikely to cover every visible behaviour outside the declared interface. The fifth gap is the summary of all of them. Unit tests are limited to the scope they cover, and because they are designed to be fast and reliable they deliberately eliminate the chaos of real dependencies, network and data. The image to keep: a unit test is like a problem in theoretical physics — ensconced in a vacuum, neatly hidden from the mess of the real world, which is great for speed and reliability and misses certain categories of defect.
Why not have larger tests A developer-friendly test must be reliable (not flaky, with a useful pass/fail signal), fast (not interrupting the workflow), and scalable (runnable efficiently across the whole change stream). Larger tests often violate all three. They are flakier because they use more infrastructure; slower both to set up and to run; and hard to scale because of resource and time requirements and because they are not isolated — they can collide with one another. Two further challenges are organisational rather than technical. Ownership: a unit test is clearly owned by whoever owns the unit, but a larger test spans multiple units and therefore multiple owners — and without clear ownership a test rots. Standardisation: unlike unit tests, larger tests lack standard infrastructure and process, because the approach is a product of a system's architectural decisions. The consequences are concrete: they are often skipped during large-scale changes because there is no standard way to run them, testing the integration between two teams requires unifying incompatible infrastructures, and no single approach can be taught to newcomers — which perpetuates the situation.
Why fidelity compounds The argument for taking fidelity seriously at scale, and against papering over it with doubles. Picture the system as a graph of services: every new node has a multiplicative effect on the number of distinct execution paths, so the number of scenarios to test end-to-end grows exponentially or combinatorially and does not scale. But the value of such tests rises too, because of the same structure: if service doubles are of lower fidelity, the chance of bugs when putting it all together is exponential in the number of them. With just two doubles that are each 10% inaccurate, the likelihood of a bug is 99%. The practical instruction that follows is counterintuitive for a chapter about big tests: even for integration tests, smaller is better — a handful of large tests is preferable to an enormous one. Because a test's scope is coupled to the scope of the system under test, making that system smaller is what makes the test smaller. And where a journey needs contributions from many internal systems, the technique is to chain it: several smaller pairwise tests where the output of one is persisted and used as the input to the next.
The four phases, and the system under test Most larger tests share a workflow: obtain a system under test; seed the necessary data; perform actions using it; verify the behaviours. The system under test is judged on two factors. Hermeticity — its isolation from usage and interaction other than the test in question; high hermeticity means the least exposure to concurrency and infrastructure flakiness. Fidelity — its accuracy in reflecting the production system, meaning binaries that resemble the production versions, similar configuration, similar infrastructure, similar topology. The forms run from a single-process system (everything in one binary, possibly with the test inside it — least faithful to production topology, but can be a small test), through single-machine and multi-machine, to a shared environment such as staging or production, with hybrids in between. The sentence to keep is that these two factors are often in direct conflict. Shared environments cost least because they already exist, and they force the test to wait until code has been pushed there, conflict with other simultaneous users, and — in production — risk end-user impact. A test in production cannot block the release of the code to that environment: the system under test is too late. Reserving windows in a shared staging environment does not scale, as the environment, its users and the likelihood of conflicts all grow.
Shrinking the system at problem boundaries Since the test's scope follows the system's scope, the highest-leverage move is choosing where to cut. Two boundaries are singled out. Interfaces: tests that involve both a front end and a back end are painful because such tests are notoriously unreliable and costly — the look and feel changes in ways that break tests without affecting behaviour, and asynchronous behaviour is hard to test. Where the back end offers a public interface it is often easier to split the tests at that boundary and drive the end-to-end tests through it. Third parties: they may offer no shared environment for testing and there can be a cost per call, so it is not recommended to have automated tests use a real third-party interface — that dependency is an important seam at which to split. The other technique is record and replay. A larger test runs continuously and its primary purpose is to generate traffic logs by recording calls to external services; a smaller test replays them during development. Because of nondeterminism, requests must be matched to decide which response to replay — which makes it very similar to stubbing, in that argument matching determines the resulting behaviour. When client behaviour changes significantly a request may no longer match, so the recording run must be easy, fast and stable to repeat.
Test data and verification A large test needs two kinds of data: seeded data, preinitialised into the system to reflect its state at the start, and test traffic, sent to it during execution. Seeding is orders of magnitude more complex than a unit test's setup. Three difficulties: domain data that must be prepopulated or the binaries fail on startup; a realistic baseline, since a system will not be perceived as realistic without enough base data of the right quality and quantity — a social network's tests need a realistic graph before anyone accepts them; and seeding interfaces, since writing directly to a datastore may bypass the triggers and checks the real binaries perform. Data can be hand-crafted, copied from production, or sampled — where smart sampling copies the minimum needed for maximum coverage. Verification comes in three kinds with different costs. Manual, where humans interact with the system — and manual regression testing does not scale sublinearly: the larger the system and the more journeys through it, the more human time is needed. Assertions, as in a unit test — explicit checks on intended behaviour. And differential comparison, which runs two copies, sends the same data and compares outputs — where the intended behaviour is not explicitly defined, so a human must go through the differences to decide whether the changes were intended.
Keeping larger tests usable Four disciplines: make them fast, drive out flakiness, make failures intelligible, and give them owners. Speed: the best move is to reduce scope or split one test into two that run in parallel. Replace time-based sleeps with polling at microsecond frequency, an event handler, or a subscription — tests that rely on sleeps and timeouts all start failing when the fleet becomes overloaded, which spirals, because those tests are then rerun more often. Make production's internal timeouts tunable, since a system configured for a distributed deployment may be running on one machine here. Flakiness: minimising it starts with reducing scope — a hermetic system avoids the multi-user flakiness of a shared environment, and a single-machine one avoids network and deployment flakiness. There is a subtle trap in internal timeouts: a production system limits end-user exposure by handling internal failures gracefully, so a service that cannot produce a result in time may return a degraded response rather than an error — which looks to a test runner like broken code when it is actually a flaky timeout. Understandability: a stack trace is not useful when the call chain crosses process boundaries, so a good failure must name what failed in context rather than saying “assertion failed”, produce a trace across the call chain or automation that narrows the culprit, and provide support and contact information. Ownership: larger tests must have documented owners who can review changes and support failures; integration tests of one project belong to its lead, and feature-focused tests to a feature owner, who must be empowered, able to support maintenance, and incentivised to do so.

Concept boundary — the vacuum is the feature, and the bill for it comes here

What it sounds like: a hierarchy of thoroughness. Unit tests are the quick check, larger tests are the real check, and a mature team simply has more of the latter — with the pyramid as a budgeting compromise for teams who cannot afford them.
What it actually is: a statement that the two kinds answer different questions because they were built by removing different things. A small test is fast and repeatable because it has removed the network, the configuration, the concurrency, the volume and the other services. Those removals are not incidental — they are the entire source of its speed and determinism, and they are simultaneously the exact list of things it can no longer see. That is why the five gaps read like an inventory of what the vacuum excluded, and why no quantity of unit tests closes them.
Why that matters practically: it stops you arguing about coverage and starts you arguing about risk. The question a larger test answers is never “is this code correct” — smaller tests do that better and cheaper. It is “does this hold once the removed things are put back”: does the configuration load, does it survive the volume, do the doubles match what the real service does, does anything emerge that no single component expresses. And that framing tells you which larger test to write, because each type in the catalogue puts back a different removed thing.
The trap: treating fidelity as free, and therefore always choosing more of it. Fidelity conflicts with hermeticity, and every step toward the real environment buys truthfulness with reliability, speed and — at the production end — actual user risk. Hence the instruction that sounds paradoxical in a chapter about big tests: make them as small as you can while still retaining the fidelity you needed them for, because the scope of the test follows the scope of the thing you chose to stand up.

Answer key

Part 1 · Q1 — the 55-minute suite

(a) The typical test is broad in scope — it validates the interaction of several distinct parts rather than the logic of one class or method — and large in size, since it runs a real database and a real message broker as separate processes and is not confined to a single machine. The suite's shape is the ice cream cone: many end-to-end tests and few integration or unit tests. Two properties attach to it: such suites tend to be slow, unreliable and difficult to work with, and the pattern often appears in projects that start as prototypes and are quickly rushed to production, never stopping to address testing debt. (b) Forty spurious failures in four thousand tests is 1% flakiness, which is exactly the stated danger line: as you approach 1% flakiness the tests begin to lose value, because it does not take needing to investigate many flakes before a team loses trust in the test suite — after which engineers stop reacting to test failures, eliminating any value the suite provided. The rerun rule is a legitimate technique misapplied. Rerunning failures automatically is effectively trading processor cycles for engineering time, and at low levels of flakiness that trade-off makes sense — but this is not a low level, and in any case rerunning a test is only delaying the need to address the root cause. Worse, a rule that merges on either green is the operational definition of no longer reacting to failures at all. (c) First, coverage measures only that a line was invoked, not what happened as a result — it is possible to exercise a lot of lines with a few tests while never checking that each line does anything useful. The figure here is additionally inflated, because coverage should be measured from small tests only, to avoid the coverage inflation that occurs when executing larger tests, and this suite is almost entirely large. Second, like other metrics it quickly becomes a goal unto itself: a bar set at 80% is treated as a ceiling rather than a floor, which is precisely why the number has not moved in a year. What should be asked instead is behavioural: do you have confidence that everything your customers expect to work will work; do you feel confident you can catch breaking changes in your dependencies; are your tests stable and reliable? Trying to answer “do we have enough tests?” with a single number ignores a lot of context and is unlikely to be useful. (d) Responsibility sits with the payments team. The rule is to test everything that you don't want to break — if you want confidence that a system exhibits a particular behaviour, the only way to be sure is to write an automated test for it — and it is stated in exactly this situation: if unrelated infrastructure changes pass all of your tests but still break your team's product, you are on the hook for fixing it and adding the additional tests. So the team owes the fix and the missing test on the date-parsing behaviour it was relying on, rather than a request for more care from the library team.

Part 1 · Q2 — the sleeping helper and the reviewer

(a) Six hundred tests at 400 milliseconds each is 240 seconds — four minutes — added to every single run of the suite. The antipattern is unnecessary speed limits introduced by sleep and timeout functions, which are often used as naive heuristics before checking the result of nondeterministic behaviour: half a second here or there does not seem dangerous, but embedded in a widely used utility it soon adds minutes of idle time to every run. The recommended replacement is to actively poll for the state transition with a frequency closer to microseconds, and the safeguard is to combine that with a timeout value in case the test fails to reach a stable state. (b) Both objections are wrong, and they are wrong in opposite directions. The date-conversion test is narrow in scope — it validates one method — but it cannot be small, because a small test must run in a single process and may not perform I/O, and reading a 200 MB offset file from disk is I/O; it is medium in size and narrow in scope. The nightly-report test is the mirror image: broad in scope, since it covers ingest, aggregation and formatting together, yet small in size, because everything out-of-process has been replaced by an in-process stand-in and the whole thing runs in one process without I/O or blocking calls. The general point is the one the reviewer is missing: size and scope are interrelated but distinct concepts. Narrow tests tend to be small and broad tests tend to be medium or large, but this is not always the case — and “unit test” names a scope, not a size. (c) The researcher performed exploratory testing: a fundamentally creative endeavour in which someone treats the application under test as a puzzle to be broken, perhaps by executing an unexpected set of steps or by inserting unexpected data. Its defining property is that the specific problems to be found are unknown at the start — they are gradually uncovered by probing commonly overlooked code paths or unusual responses. The omitted step is the one that makes it pay twice: as soon as an exploratory test discovers an issue, an automated test should be added to prevent future regressions, so that a flaw found once by a human can then be checked continuously and at scale. (d) The target is roughly 80% narrow-scoped unit tests validating the majority of the business logic, 15% medium-scoped integration tests validating interactions between two or more components, and 5% end-to-end tests validating the entire system — by test case count, with every team's mix a little different. The reasoning: unit tests form an excellent base because they are fast, stable, dramatically narrow the scope and reduce the cognitive load required to identify all the possible behaviours a class or function has, and because they make failure diagnosis quick and painless; the recommended mix is determined by two goals, engineering productivity and product confidence, and favouring unit tests gives high confidence quickly and early in development. What the largest tests should not be relied on for is stated plainly: larger tests act as sanity checks as the product develops; they should not be viewed as a primary method for catching bugs.

Part 2 · Q1 — nineteen breakages and one shipped bug

(a) The nineteen breakages are brittleness: a brittle test is one that fails in the face of an unrelated change to production code that does not introduce any real bug. Its look-alike is a flaky test, which fails nondeterministically, without any change to production code at all — same loss of trust, different cause and different cure. The change described is a pure refactoring: the internals changed and the interface did not. Since tests should not need to change during a pure refactoring, and their whole role in that case is to ensure the refactoring did not change behaviour, breakage proves one of exactly two things — either the change is affecting the system's behaviour and is not a pure refactoring, or the tests were not written at an appropriate level of abstraction. Here the interface was untouched, so it is the second. (b) The practice is to test via public APIs: write tests that invoke the system being tested in the same way its users would, calling its public surface rather than its implementation details. The argument is definitional — if tests work the same way as the system's users, then by definition a change that breaks a test might also break a user; such tests form explicit contracts, and testing only those contracts means you are free to do whatever internal refactoring you want without having to worry about making tedious changes to tests. “Public” in this context means the API exposed by that unit to third parties outside of the team that owns the code, which does not always align with the notion of visibility provided by some programming languages. (c) The test verifies that a specific call was made against a collaborator, and such tests fail in two directions. In the first, a bug leaves the system in the wrong state even though the call was made, so the test passes even though we would have wanted it to fail — which is exactly the shipped bug: append() was called once with the right argument, the assertion was satisfied, and nothing was ever made durable, because verifying a call says nothing about what the call resulted in. In the second, the system is refactored to call a slightly different API to write an equivalent record, and the test fails even though we would have wanted it to pass. The alternative is to test directly against the state of the system: perform the action and then read the state back, which more accurately expresses what we care about — the state of the system under test after interacting with it. (d) The proposed rule entrenches the defect. It treats the internal structure as something the tests are entitled to depend on, which is precisely what makes them brittle, and it accepts a permanent tax on refactoring — over time that friction makes a team reticent to perform necessary refactoring to keep a codebase healthy. It also concedes the automation: if a set of tests needs to be manually tweaked by engineers for each change, calling it an “automated test suite” is a bit of a stretch. The correct move is to rewrite the tests against the public surface and to assert on resulting state — after which the array swap, the inlining and the handle change would have broken nothing, and the uncommitted-reservation bug would have failed a test, because reading the ledger back would have found it empty.

Part 2 · Q2 — the sixty-line test

(a) The mistake is framing tests around methods — matching the structure of the tests to the structure of the code, such that every production method has a corresponding test method. It is convenient at first and degrades: as the method being tested grows more complex, its test also grows in complexity and becomes more difficult to reason about, and it naturally encourages unclear tests because a single method often does a few different things under the hood and might have several tricky edge and corner cases. The alternative unit is the behaviour: any guarantee that a system makes about how it will respond to a series of inputs while in a particular state, expressible as given, when and then — and the mapping between methods and behaviours is many-to-many. Three reasons behaviour-driven tests read better: they read more like natural language, allowing them to be naturally understood rather than requiring laborious mental parsing; they more clearly express cause and effect because each test is more limited in scope; and because each is short and descriptive, they make it easier to see what functionality is already tested and encourage engineers to add new streamlined test methods instead of piling onto existing ones. (b) The catch-all helper damages intent and localisation: tests using a fixed validation strategy are less behaviour driven, it becomes much more difficult to determine the intent of any particular test and to infer what exact case the author had in mind, and when bugs are introduced such helpers make them more difficult to localise because they will frequently cause a large number of tests to start failing. The corrective rule: the best validation helper methods assert a single conceptual fact about their inputs, and earn their place when that condition is conceptually simple but requires looping or conditional logic that would reduce clarity inside the test body. The setup values damage completeness: a test that depends on a particular value defined in setup seems incomplete because a reader needs to go hunting to discover where it came from. The corrective rule: tests that explicitly care about particular values should state those values directly, overriding the default defined in the setup method if need be — the result contains slightly more repetition and is far more descriptive and meaningful. (c) The test builds its expectation the same way the code builds the result, so both can be wrong in the same way and the test cannot detect it. The rule broken is don't put logic in tests: clear tests are trivially correct upon inspection, and logic — operators, loops, conditionals — means you need to do a bit of mental computation to determine the result instead of just reading it off the screen; the worked case is a single string concatenation that concealed a doubled separator until the value was written out in full. And if you feel like you need to write a test to verify your test, something has gone wrong. What should be tolerated instead is duplication: writing the whole expected value out, since duplicating it is a small price to pay for making the test more descriptive and meaningful — stick to straight-line code over clever logic. (d) A good failure message clearly expresses the desired outcome, the actual outcome, and any relevant parameters. A rewrite: “Expected a cart total of 1104 after applying the 15% discount to an item priced 1299, but the total was 1299.” Note why the generic form arises: an assertion that receives only a boolean value can only give a generic message such as “expected true but was false”, whereas one that explicitly receives the subject of the assertion can report what the value actually was.

Part 3 · Q1 — the notifications service

(a) Two techniques are in use. Stubbing — giving behaviour to a function that otherwise has no behaviour of its own, by specifying exactly what values it returns — supplies the six canned values. Interaction testing — validating how a function is called without actually calling the implementation of the function — supplies the two verifications. A green test claims correspondingly less at each. With stubbing, it claims the system behaved correctly on the assumption that the author's beliefs about the dependencies were accurate, because with stubbing there is no way to ensure the function being stubbed behaves like the real implementation. With interaction testing, it claims only that certain functions were called as expected: it cannot tell you that the system under test is working properly, and it requires you to make an assumption about the behaviour of the code. (b) The 140 failures are the signature of change-detector tests — tests that overuse interaction testing and therefore fail in response to any change to the production code, even if the behaviour of the system under test remains unchanged. What is being asserted instead of the intended behaviour is implementation detail: to validate that a function was called, you are exposing to the test that the system under test calls this function, which leaks implementation details of production code into the tests and is what makes them brittle. (c) Two failures compound. The interaction check on the delivery call proves the call happened, and the primary issue with interaction testing is precisely that it can only validate that certain functions are called — it cannot establish that the send succeeded. And the stubbing hardcodes part of the contract: every canned receipt sets the accepted flag true, which is the danger that tests become less effective — you will be forced to duplicate the details of the contract, and there is no way to guarantee that the contract is correct, that is, that the stubbed function has fidelity to the real implementation. There is a further consequence here: with stubbing there is no way to store state, so the test could not have queried the delivery client for what had actually been recorded even if it had wanted to. (d) Four moves, in order. First, ask the owners of the API to create a fake — they may not be familiar with the concept, or may not realise the benefit it provides to users of their API. Second, if they are unwilling or unable, write your own, which can be done by wrapping all calls to the API in a single class and then creating a fake version of that class; this is often much simpler than faking the entire API, since you generally need only a subset of its behaviour. Third, settle on using a real implementation and accept its trade-offs. Fourth, resort to other test double techniques and accept theirs. On ownership and placement: the team that owns the real implementation should write and maintain the fake, because whenever the behaviour of the real implementation changes the fake must be updated to match; and to limit how many exist, a fake should typically be created only at the root of the code that isn't feasible for use in tests — for a database, at the database API itself rather than for each class that calls it.

Part 3 · Q2 — four dependencies in a booking engine

(a) The money type: use the real one. A real implementation is preferred if it is fast, deterministic and has simple dependencies, and a real implementation should be used for a value object — an amount of money, a date, an address, a collection class. “Doubles are the standard here” is not a criterion. The pricing library: keep it real. The arithmetic is 1.2 milliseconds across 900 cases, which is 1.08 seconds added to the whole suite. There is no exact answer on how slow is too slow — it depends on whether engineers feel a loss in productivity and on how many tests use the implementation, since one second extra per test case may be reasonable if there are five test cases but not if there are 500 — and for borderline situations it is often simpler to use a real implementation until it becomes too slow to use, at which point the tests can be updated. Roughly a second across the whole suite is not that point. (b) The seat allocator is nondeterministic: a test is nondeterministic if its outcome can change even when the system under test remains unchanged, and nondeterminism leads to flakiness. Two causes apply: a more complex real implementation is likelier to be nondeterministic, for instance where output depends on thread execution order, and code that relies on the system clock, whose output differs with the current time; the fix for the latter is that instead of relying on the system clock, a test can use a test double that hardcodes a specific time. The test for whether flakiness warrants a response: if use of a real implementation rarely causes flakiness it might not warrant a response, because there is little disruption to engineers — but if flakiness happens often, it might be time to replace the real implementation with a test double. (c) The technique is stubbing, which is appropriate here for the reason that distinguishes it: because a function's behaviour is defined inline in the test, stubbing can simulate a wide variety of return values or errors that might not be possible to trigger from a real implementation or a fake. Two constraints keep it honest: each stubbed function should have a direct relationship with the test's assertions, so its purpose is clear; and a test should typically stub out a small number of functions, because stubbing many leads to less clear tests and can be a sign that stubbing is being overused, or that the system under test is too complex and should be refactored. So keep the fake for everything else and stub only the declined-after-authorisation path. On the fake itself: a fake might not need to have 100% of the functionality of its corresponding real implementation, especially if such behaviour is not needed by most tests — for example, error handling code for rare edge cases — and in that case it is best to have the fake fail fast, raising an error if an unsupported code path is executed, which communicates to the engineer that the fake is not appropriate in this situation. (d) The technique is interaction testing, justified by the second warranted case: differences in the number or order of calls to a function would cause undesired behaviour, and it is useful because it could be difficult to validate this behaviour with state testing. That is the situation exactly: the provider is external, so there is no state to read back, and the only observable difference between working and broken is the number of calls. It sits inside the general restriction rather than at its edge — perform interaction testing only for state-changing functions, those with side effects on the world outside the system under test, and dispatching a confirmation is one, whereas for non-state-changing functions the check is usually redundant, given that the system under test will use the return value to do other work that you can assert. And when writing it, avoid overspecification — verify the minimum necessary for the behaviour in question.

Part 4 · Q1 — four incidents and a coverage plan

(a) The routing table: configuration issues. Unit tests cover code within a binary, but that binary is typically not completely self-sufficient in terms of how it is executed — there is usually a deployment configuration or starter script, and production instances have their own configuration files; issues with these files, or with the compatibility between the state they define and the binary, can lead to major user issues, and unit tests alone cannot verify this compatibility. The partner's new error code: unfaithful doubles. When a heavyweight dependency is replaced it becomes possible that the replacement and the doubled thing do not agree: the engineer writing the test defines the double, and usually did not write the thing being doubled and can be misinformed about its actual behaviour, so the understanding of the contract is invalid. Worse, doubles become stale — if the double is invisible to the author of the real implementation and that implementation changes, there is no signal that the test should be updated. The twelvefold traffic: issues under load. Such testing requires sending large volumes of traffic, which does not fit a typical unit test — and load and stress handling are highly emergent properties: complex behaviours that belong to the overall system but not the individual members, which is why no component exhibited the collapse alone. The sorting order: unanticipated behaviours. Unit tests are limited by the imagination of the engineer writing them — they can only test for anticipated behaviours and inputs, while the issues users find are mostly unanticipated. (b) Two practices. For configuration: keep it in version control as well as your code, because then changes to configuration can be identified as the source of bugs rather than introducing random external flakiness, and can be built into large tests — precisely what a separate unreviewed repository prevents. For doubles: if teams provide fakes for their own services, this concern is mostly alleviated, since a fake maintained by the owning team tracks real behaviour instead of encoding a consumer's guess. (c) The sorting incident is an instance of Hyrum's Law: even if we could test 100% for conformance to a strict specified contract, the effective user contract applies to all visible behaviours, not just a stated one, and it is unlikely that unit tests alone test for all visible behaviours not specified in the public API. More unit tests cannot close it, because you can only write a test for a behaviour you have thought of — and these are by definition the ones nobody specified. The type of larger test that does address it is differential comparison, which detects unanticipated side effects without requiring anyone to state the expectation in advance. (d) The plan is aimed at the wrong axis: none of the four incidents is a defect in code logic inside a binary, which is what unit tests and coverage bear on — and coverage only measures that a line was invoked, not what happened as a result. What the diagnosis calls for is a set of larger tests, each putting back a different removed thing: deployment configuration testing, really a smoke test — if the system under test starts successfully the test passes, and if not it fails; a fake for the partner service, requested from its owners; performance, load and stress testing built to look as close to production as possible; and differential regression testing for the unanticipated — plus the configuration file into version control.

Part 4 · Q2 — the checkout journey

(a) Hermeticity — isolation from usages and interactions other than the test in question, giving the least exposure to concurrency and infrastructure flakiness — and fidelity, accuracy in reflecting the production system. These two factors are often in direct conflict. This design sits at low hermeticity, since shared staging and a live external sandbox mean the test might conflict with other simultaneous uses, bought with high environmental fidelity. Scheduling it after deployment is decisive: such tests cannot run until the code reaches that environment, so they cannot block its release — the system under test is too late. (b) Two boundaries. Between front end and back end: user interface tests are notoriously unreliable and costly, since interfaces often change in look-and-feel ways that make the tests brittle but do not actually impact the underlying behaviour and often have asynchronous behaviours that are difficult to test — so where the back end provides a public interface, split the tests there and use it to drive the end-to-end tests. The third-party boundary: such systems might not have a public shared environment for testing, and there can be a cost with sending traffic to a third party, so it is not recommended to have automated tests use a real third-party API — that dependency is an important seam at which to split tests. (c) Direct database seeding breaks the seeding-interface point: writing directly to a datastore might bypass triggers and checks performed by the actual binaries that perform the writes, so the state may be one production could never produce. The sleeps break the speed and flakiness guidance: naive tests use time-based sleeps to wait for nondeterministic action, but real production users want to wait as little as possible, so tests should react the way they would. The replacements: polling at a frequency closer to microseconds, with a timeout; an event handler; or a subscription to a notification system. The failure mode under load is a spiral: tests relying on sleeps all start failing when the fleet running them becomes overloaded, and that spirals, because they are then rerun more often, increasing the load further. (d) Three things. Clearly identify what the failure is: the worst case is an error that just says “assertion failed” and a stack trace, where a good one anticipates the runner's unfamiliarity and gives context. Minimise the effort of identifying the root cause, since a stack trace is not useful when the call chain spans process boundaries — produce a trace across that chain, or automation that narrows the culprit. And provide support and contact information. On ownership: larger tests must have documented owners who can review changes and be counted on for support when the test fails; without one, the test is harder to update, failures take longer to resolve — and the test rots. Integration tests belong to the project lead and feature tests to a feature owner — empowered, able to maintain it, and incentivised to.
